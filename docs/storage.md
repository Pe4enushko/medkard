# Хранилища и жизненный цикл карт

Код слоя хранения находится в `src/storage/`. Все его классы наследуются от
`BaseStorage` и используют общий асинхронный пул psycopg3. Векторный RAG живёт
отдельно в `RAG/retrieval/vector_store.py` и использует собственный пул
asyncpg: это два независимых клиента одной PostgreSQL.

## Основные хранилища

| Класс | Назначение |
|---|---|
| `DoneCardsStorage` | Входные данные карты, результаты аудита и терминальные состояния |
| `OrganizationsStorage` | Организации и их идентификаторы |
| `GuidelinesStorage` | Метаданные клинических рекомендаций |
| `DocsStorage` | Чанки клинических рекомендаций и их метаданные |
| `IngestRunsStorage` | История загрузки документов |
| `DrugsStorage` / `DietarySupplementsStorage` | Legacy-справочники лекарств и БАД |

## `done_cards`

`status` описывает завершённость обработки, а `ignored` и `broken` — исход:

| Состояние | Поля | Смысл |
|---|---|---|
| Ожидает аудита | `status='pending'` | Карта записана, результаты ещё не рассчитаны |
| Проверена | `status='done'`, `ignored=FALSE`, `broken=FALSE` | Результаты аудита сохранены |
| Отфильтрована | `status='done'`, `ignored=TRUE` | Весь приём исключён фильтром, результатов аудита нет |
| Упала | `status='done'`, `broken=TRUE` | Сохранены исходная карта и стектрейс |

Ограничение миграции 014 запрещает карте одновременно иметь
`ignored=TRUE` и `broken=TRUE`.

Основные методы записи:

- `upsert()` сохраняет успешный результат и снимает `broken`;
- `upsert_ignored()` сохраняет отфильтрованную карту и снимает `broken`;
- `upsert_broken()` сохраняет исходную карту и свежий стектрейс;
- `upsert_pending()` очищает прежний результат и переводит обновлённую карту в
  ожидание аудита.

## Выборки для очередей и переаудита

- `get_pending(organization_id=None)` возвращает ожидающие карты одной
  организации. Здесь `None` означает строки с `organization_id IS NULL`.
- `get_done_guids(organization_id=None)` возвращает терминальные GUID одной
  организации. В выборку входят и broken-карты: у них `status='done'`, поэтому
  обычный ночной прогон считает их уже обработанными и не повторяет аудит.
- `get_broken(organization_id=None)` возвращает карты, пригодные для
  переаудита: `broken=TRUE`, `card_data IS NOT NULL`, `card_guid IS NOT NULL`.
  В отличие от двух методов выше, `None` здесь означает все организации —
  вызывающий код должен сгруппировать строки самостоятельно. Карты без GUID не
  выбираются, потому что результат нельзя надёжно записать обратно в исходную
  строку.
- `get_states_for_guids(guids)` одним запросом возвращает `broken`, `ignored`
  и `stacktrace`. Метод нужен для сверки результата переаудита по состоянию БД,
  а не по возврату пайплайна.

## Переаудит broken-карт

Скрипт `scripts/fix-broken.py` работает офлайн относительно 1С: берёт
сохранённый `card_data`, группирует карты по `organization_id` и для каждой
группы создаёт отдельный `AuditPipeline` с её фильтром. Вызов
`run_batched(..., done_guids=set())` отключает только дедупликацию; обычные
фильтры организации продолжают действовать.

```bash
python scripts/fix-broken.py Alenka --dry-run
python scripts/fix-broken.py --all -y --num-batches 5
```

После прогона скрипт повторно читает состояние выбранных GUID и разделяет их
на три группы:

- `fixed` — карта больше не broken и не ignored;
- `moved to ignored` — карта попала под действующий фильтр;
- `still broken` — аудит снова упал; выводится последняя строка свежего
  стектрейса.

Полный отказ PostgreSQL не считается деградацией отдельного узла: без БД
нельзя ни прочитать карту, ни выполнить RAG, ни сохранить результат или аудит.

## JSON результата диагноза

`diag_result[]` хранит агрегат источников внутри каждого диагноза в поле
`guideline_sources`; источники конкретного замечания остаются в
`issues[].sources`. Полный контракт описан в [visits-api.md](visits-api.md).
