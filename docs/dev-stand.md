# Локальный dev-стенд

Быстрый способ получить базу, на которой можно гонять аудит и e2e, не трогая
прод. Один вход:

```bash
bash scripts/dev/dev_stand.sh
```

Оркестратор задаёт все вопросы и запускает три стадии по очереди. Каждая стадия
— отдельный скрипт, аргументы вместо вопросов, поэтому её можно запустить одну.

| Стадия | Скрипт | Что делает |
|---|---|---|
| 1 | `scripts/dev/deploy_dev.sh` | поднимает контейнер, создаёт роль и базу, включает `vector` и `pg_trgm`, накатывает `migrations/*.sql`, пишет креды в `.env.dev` |
| 2 | `scripts/dev/fill_dev.sh N` | копирует данные из источника: справочники целиком, карты за N дней |
| 3 | `scripts/dev/switch_env.sh` | бэкапит `.env` и заменяет в нём строки `POSTGRES_*` на стендовые |

## Что где лежит

- **`docker-compose.dev.yml`** — один сервис `db` на образе `pgvector/pgvector:pg16`,
  том `medkard-dev-db`, порт `127.0.0.1:55432`. Слушает только петлю, поэтому
  внутри контейнера стоит `trust`: пароля суперпользователя нет и хранить его
  негде. Порт меняется через `MEDKARD_DEV_PORT`.
- **`.env.dev`** — то, чем стадии связаны между собой. Стадия 1 его пишет,
  стадия 2 берёт оттуда цель, стадия 3 — источник для правки `.env`. В git не
  идёт.
- **`.env`** — источник данных для стадии 2 и рабочий конфиг приложения. Стадия
  2 читает его только на чтение; менять его — работа стадии 3, и та сначала
  делает копию `.env.bak.<дата>`.

Вернуться на прежнюю базу — скопировать бэкап обратно:

```bash
cp .env.bak.2026-09-29-094815 .env
```

## Стадия 2 подробнее

Источник по умолчанию — `POSTGRES_*` из `.env`. Другой источник (реплика,
чужой дамп, локальная база для проверки самого скрипта) задаётся так:

```bash
MEDKARD_SRC_ENV=~/.medkard-replica.env bash scripts/dev/fill_dev.sh 14
```

Скрипт отказывается работать, если источник и цель — одна и та же база.

Целиком копируются `organizations`, `api_keys`, `api_key_organizations`,
`guidelines`, `docs` (вместе с эмбеддингами), `ingest_runs`, `drugs`,
`dietary_supplements`, `grls_imports`, `grls_registry`. Окном по дате —
`done_cards` и `push_log`: в них десятки тысяч строк, а стенду нужна выборка,
а не архив. Порядок таблиц учитывает внешние ключи, перед вставкой каждая
таблица цели очищается, поэтому скрипт можно запускать повторно.

Копирование идёт через `psql \copy`, а не `pg_dump`: не нужно совпадение версий
клиента и двух серверов, и это единственный способ отфильтровать строки по дате
за один проход.

## Обезличивания здесь нет

`done_cards.card_data` несёт `ДанныеОсмотра` в том виде, в каком их прислала 1С,
а там на практике встречаются ФИО и СНИЛС законного представителя. Копирование
карт кладёт это на машину разработчика. Так решено осознанно при проектировании
стенда; если понадобится наоборот — это отдельная работа, и её место в стадии 2.

## Прогон e2e после стенда

```bash
e2e/run-diagnosis-graph-tests.sh deterministic
```

Тестам нужна не только база, но и LLM: ключи и модель остаются в `.env` теми же,
стадия 3 их не трогает.

Логи прогона и как их отдать на другую машину — в `docs/e2e-testing.md`, раздел
«Run logs». Коротко: `scripts/dev/send_logs.sh <ssh-алиас>`.
