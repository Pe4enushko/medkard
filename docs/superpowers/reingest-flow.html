Reingest with resume — от папки до завершения

Как файлы из pdfs/ и строки manifest.csv синхронизируются с таблицами docs и guidelines, переживая прерывания и перегоняя LLM только когда это правда нужно.

Вход · оператор

pdfs/<file_id>.pdf

новые / изменённые / откатанные PDF

resources/manifest.csv

строки: ID + метаданные (Наим., МКБ-10, возраст…)

первый прогон / после смены схемы БД — один раз

Разовая подготовка

bash migrations/migrate.sh

→ docs, guidelines, ingest_runs (019–023)

python scripts/seed-guidelines.py

→ guidelines := снимок манифеста «как есть»

Запуск

python scripts/reingest-pdfs.py [--only-failed] [--file-id ID]

Сбор состояния

manifest_rows ← manifest.csv

runs ← ingest_runs (status, content_hash)

guidelines ← таблица guidelines («старый» манифест)

current_hash ← sha256(pdfs/<id>.pdf) для каждого id

build_worklist → classify(file_id) на каждый файл
FULL

нет записи в runs · status != done · хеш PDF изменился (в т.ч. откат)

→ полный re-chunk + upsert guidelines

METADATA_ONLY

done, хеш тот же, но строка манифеста ≠ guidelines

→ upsert guidelines · дёшево, без LLM · docs и ingest_runs не трогаем

SKIP

done + хеш совпал + манифест совпал

→ ничего

FULL ветка полного reingest — на один файл

  1. upsert ingest_runs(id, status='pending') — content_hash сохраняем
  2. load_documents(only={id}) → iter_chunks() — fitz: секции 3-ур. regex + таблицы
  3. process_batch → LLM queries + embeddings — самая медленная и хрупкая часть
  4. replace_by_file_id(id, docs) — атомарно: DELETE + INSERT в одной транзакции
  5. guidelines.upsert_many([Guideline.from_manifest_row])
  6. mark_done(id, content_hash=current_hash) — ПОСЛЕДНИМ: точка «файл готов»
  7. Exception → mark_failed(id, error) — логируем и идём к следующему файлу

Завершение · прерывание · повтор

Ctrl+C / падение между файлами — текущий файл уже done либо остался pending/failed.

Ctrl+C посреди файла — docs-транзакция атомарна (нет полу-записи), но mark_done не дошёл → status='pending'.

Повторный запуск → build_worklist заново: pending/failed/нет записи → переделать; done + хеш + манифест совпали → skip.

SELECT status, count(*) FROM ingest_runs GROUP BY status;

Три инварианта корректности

Хеш решает re-chunk.

Дорогая LLM-генерация — только если sha256(PDF) разошёлся с последней done-записью. Смена одних метаданных → дешёвый upsert guidelines.

mark_done последним.

Крах в любой момент оставляет файл не-done → следующий прогон переделает его идемпотентно, без ручного вмешательства.

content_hash пишется только на done.

pending/failed его сохраняют — сравнение всегда с последним успешным состоянием, поэтому откат файла ловится как «изменился».
