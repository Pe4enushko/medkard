# check_updates endpoint — Design

## Проблема

Направление данных: medkard сам забирает визиты организаций (Alenka, MDS) из их 1C
(ночной прогон `scripts/audit-one-c-period.py`), либо принимает push-обновления карт
от 1C через `POST /cards/push`. medkard их аудирует и складывает результат в
`done_cards`.

Заберить уже проаудированные результаты у medkard должна Искра — отдельное
приложение (репозиторий `engine`), в котором врач через нейронку обсуждает карты
пациентов. Искра сейчас делает это двумя способами (модуль
`engine/src/engine/integrations/medcheck/`):

- `GET /cards/pull?date=` — xlsx-отчёт за конкретный день (`MedcheckClient.pull`).
- `GET /cards/export?since=&limit=&cursor=` — JSON-выгрузка строк `done_cards`,
  клиент-управляемый курсор по `updated_at`, отфильтрованная по
  `ignored = FALSE AND broken = FALSE` (только аудированные карты); Искра сейчас
  вызывает его с `since=None` раз в сутки и делает `TRUNCATE` + полный перезалив
  своей реплики (`run_replica` в `importer.py`/`exporter.py`), без инкрементального
  курсора на своей стороне.

Обе модели рассчитаны на периодический (обычно ночной/дневной) пул. С появлением
`POST /cards/push` (см. `2026-07-21-cards-push-endpoint-design.md`) 1C может в любой
момент обновить уже поданную карту — она уходит в `status='pending'`, старые
результаты аудита стираются, и карта ждёт ночной переаудит. Искре сейчас неоткуда
узнать об этом раньше следующего планового пула.

Нужен лёгкий эндпоинт, который Искра может опрашивать часто (раз в 30 секунд) и
получать снимок того, что изменилось с прошлого раза — включая карты, которые ещё не
проаудированы (`pending`), а не только готовые результаты.

Это не второстепенное удобство: `done_cards` — единственное место, где medkard
хранит сырые данные карты (`card_data`) вообще, независимо от того, дошла ли она до
аудита. Искра даёт врачу возможность обсудить с нейронкой любую карту, включая ту,
что ещё не проаудирована (`pending`) или помечена `ignored`/`broken` — то есть Искре
нужен доступ к сырым данным карты сам по себе, а не только к результатам аудита.
Именно поэтому `check_updates` не может переиспользовать фильтр `export`
(`ignored = FALSE AND broken = FALSE`, только аудированные) — это его ключевое
отличие, а не побочная деталь.

## Требования

- Новый эндпоинт `GET /cards/check_updates`, авторизация как у остальных card-роутов
  (`require_org_access`, ключ scoped на организацию через `?org=`).
- Возвращает **снимок текущего состояния** изменившихся карт: одна строка на
  `card_guid`, с его состоянием на момент опроса. Никакого event-log — если карта
  дважды поменялась между опросами, клиент увидит только последнее состояние.
- Включает **все статусы**: `pending`, `done`, а также `ignored`/`broken` (в отличие
  от `export`, который сейчас исключает ignored/broken). Обоснование: Искре нужны
  сырые данные карты (`card_data`) сами по себе, чтобы врач мог обсудить с нейронкой
  даже ещё не проаудированную или нераспознанную карту — не только готовые
  результаты аудита.
- Курсор **server-side**, привязан к паре (api_key_id, organization_id) — не
  клиент-управляемый `since`, как в `export`. Сервер сам помнит, что последний раз
  отдал этому ключу по этой организации, и на каждый ответ продвигает курсор вперёд.
  Клиенту не нужно хранить и передавать никакого состояния между опросами.
- Курсор продвигается **сразу при формировании ответа** (в той же транзакции, что и
  чтение) — без двухфазного подтверждения (`ack_until`). См. "Надёжность доставки"
  ниже за обоснование.

## Надёжность доставки — принятое решение

Рассматривались два варианта: простой курсор (продвигается сразу) и `ack_until`
(двухфазное подтверждение, клиент явно подтверждает получение перед тем, как сервер
продвинет курсор дальше).

Простой курсор рискует потерять один снимок изменений, если HTTP-ответ не дошёл до
Искры (её процесс упал/убит между отправкой запроса и обработкой ответа, либо
таймаут на её стороне сработал раньше, чем сервер успел ответить). Расследование
реальной интеграции (`engine/src/engine/integrations/medcheck/`) показало:

- HTTP-таймаут у Искры сейчас — 60s (connect 10s), намного больше 30-секундного
  интервала опроса — сценарий "таймаут на стороне Искры раньше сервера"
  маловероятен при нормальной нагрузке.
- Запрос курсора — это чтение/обновление одной маленькой строки-маркера по
  первичному ключу, не блокируется конкуренцией с ночным аудитом (тот работает
  через отдельную таблицу `done_cards`).
- У Искры уже существует **утренний страховочный пул** — `run_replica()` в
  `engine/src/engine/integrations/medcheck/importer.py` + `exporter.py`, который
  делает `TRUNCATE done_cards` + полный `since=None` пул раз в сутки через
  `MedcheckClient.export()`. Это самодостаточный full-replace, не зависящий от
  состояния check_updates-курсора — он перекрывает любую редкую потерю снимка в
  реальном времени.

**Итоговое решение:** realtime-отслеживание (`check_updates`, server-side курсор,
продвигается сразу) на стороне medkard + существующий утренний `export`-пул на
стороне Искры как страховка. Полноценная гарантия доставки (`ack_until`,
подтверждения, Kafka-очередь на стороне Искры) — предмет отдельной будущей
доработки её клиентской синхронизации, не блокирует эту итерацию.

## Архитектура

### Новая таблица: курсор на ключ+организацию

```sql
-- migrations/026_check_updates_last_seen.sql
CREATE TABLE IF NOT EXISTS check_updates_last_seen (
    api_key_id      UUID        NOT NULL REFERENCES api_keys(id)      ON DELETE CASCADE,
    organization_id UUID        NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    last_seen_at    TIMESTAMPTZ NOT NULL DEFAULT '-infinity',
    PRIMARY KEY (api_key_id, organization_id)
);
```

`-infinity` как дефолт означает "ещё ни разу не опрашивал" — первый вызов
`check_updates` для новой пары (ключ, организация) вернёт всю историю `done_cards`
для этой организации.

### Storage-слой

`src/storage/check_updates_storage.py` — новый класс на основе `BaseStorage`
(тот же паттерн, что `done_cards_storage.py`):

- `get_last_seen(api_key_id: str, organization_id: str) -> datetime` — читает
  `last_seen_at`, либо `-infinity`, если строки ещё нет (не требует отдельного upsert
  перед первым чтением).
- `advance_last_seen(api_key_id: str, organization_id: str, new_ts: datetime) -> None`
  — upsert: вставляет строку с `new_ts`, либо обновляет существующую **только если**
  `new_ts > last_seen_at` (защита от отката курсора назад при повторных/несортированных
  вызовах).
- `fetch_changed(organization_id: str, since: datetime) -> list[dict]` — читает из
  `done_cards` строки с `updated_at > since` для данной организации, **без** фильтра
  `ignored`/`broken` (в отличие от `export`). Возвращает `card_guid`, `status`,
  `ignored`, `broken`, `card_data`, `formal_result`, `diag_result`,
  `icd_check_result`, `updated_at`.

### Роут (последующая итерация — не в этой задаче)

`GET /cards/check_updates?org=<name>` в `src/api/routes/cards.py`:

1. Резолвит `api_key_id` из `require_org_access` (уточнить: сейчас
   `require_org_access` возвращает `(org_id, org_name)` — потребуется убедиться, что
   `api_key_id` тоже доступен из зависимости, либо расширить `auth.py`).
2. `last_seen = get_last_seen(api_key_id, org_id)`.
3. `rows = fetch_changed(org_id, since=last_seen)`.
4. Если `rows` непусто: `new_cursor = max(r["updated_at"] for r in rows)`;
   `advance_last_seen(api_key_id, org_id, new_cursor)`.
5. Вернуть `rows` как JSON.

Эта задача (спека) фиксирует только миграцию + storage-слой + тесты на них — они не
зависят от точной реализации роута сверху, и могут быть реализованы и провалидированы
независимо. Роут — предмет следующей задачи/плана.

## Что осталось нерешённым (не блокирует эту задачу)

- Точная форма ответа роута `check_updates` (поля, пагинация при большом объёме
  изменений — сейчас `export` поддерживает `limit`/`cursor` для бэкфилла, стоит ли
  такое же тут).
- Как `require_org_access`/`auth.py` должен передавать `api_key_id` в роут (сейчас
  отдаёт только `(org_id, org_name)`).
- Kafka/подтверждения на стороне Искры — отдельная будущая работа, не в этом репо.

## Тестирование

- Миграция: применяется идемпотентно (`IF NOT EXISTS`), проверяется как в
  `tests/test_done_cards_status_migration.py` (аналогичный паттерн для миграции 025).
- Storage: `tests/test_check_updates_storage.py` —
  - `get_last_seen` возвращает `-infinity`-эквивалент для ранее не встречавшейся пары
    (ключ, организация).
  - `advance_last_seen` создаёт строку при первом вызове, обновляет при последующих.
  - `advance_last_seen` не откатывает курсор назад при вызове с более ранним `new_ts`.
  - `fetch_changed` возвращает карты во всех статусах (pending/done/ignored/broken),
    отфильтрованные по `updated_at > since` и по `organization_id`.
  - `fetch_changed` с `since = -infinity` возвращает полную историю организации.
