# OCR для сканированных клинических рекомендаций

**Дата:** 2026-07-20 · **Ревизия:** 2026-07-20 · **Статус:** утверждён · **Ветка:** `guideline-filename-fallback`
**Связано:** `src/RAG/ingestion/data_loader.py` (`PDFContentReader.iter_chunks`), уже существующий
try/except-паттерн для tabula-ошибок (та же страница) — OCR следует тому же принципу локальной,
не фатальной деградации.

## Зачем

~22 из ~700 файлов клинреков — сканы: `PDFContentReader.iter_chunks()` полагается на `fitz`
(`page.get_text()`) для извлечения текста, что требует текстового слоя в PDF. У скана текстового
слоя нет → `full_text` пуст → 0 текстовых чанков для документа, при этом ошибки нет — файл просто
тихо не попадает в RAG. Обнаружено через `scripts/check-guidelines-integrity.py` (0 chunks у части
file_id с резолвящимся PDF) и подтверждено вручную на `206_2.pdf` (26 стр., скан) и `1003_1.pdf`
(33 стр., скан).

**Выбор движка.** Рассмотрены Tesseract, Unstructured (обёртка над тем же Tesseract), Apache Tika
(тоже делегирует OCR в Tesseract, добавляет JVM-сервер без реальной пользы для узкой задачи «только
PDF»), облачный OCR (Google/Azure/Yandex Vision) и vision-LLM. Облачные варианты отклонены — данные
хоть и не содержат сведений о пациентах (публичные клинические рекомендации), но предпочтение отдано
локальному решению без внешних сетевых зависимостей. Vision-LLM отклонён: используемая в проекте
LLM (`Qwen/Qwen3.6-35B-A3B-FP8`, self-hosted на `10.22.0.4`) текстовая, без vision — разворачивать
отдельную vision-модель ради ~22 файлов не оправдано объёмом задачи. Итог — локальный Tesseract,
уже установлен и проверен в бенчмарке ниже.

## Бенчмарк (обоснование параметров)

Проверено на реальных файлах `206_2.pdf` (нативное разрешение скана ~420 DPI, JPEG) и `1003_1.pdf`
(нативное разрешение ~200 DPI, PNG), Tesseract 4.1.1, sweep по DPI рендера (150/200/300/400) × PSM
(3/4/6) × OEM (1/3):

- **DPI рендера выше нативного разрешения скана ничего не даёт** — просто апскейл тех же пикселей.
  `1003_1` (нативно ~200 DPI): char count и cyrillic/word-ratio почти не менялись между dpi=150 и
  dpi=400 (1846–1877 симв., cyr_ratio 0.818–0.830). Рендер на 300 DPI — безопасный дефолт с запасом
  для более качественных сканов, без реальной пользы от 400.
- **PSM (3/4/6) и OEM (1/3) не дали значимой разницы** на этих файлах — OEM 3 (auto) резолвится в
  OEM 1 (LSTM), т.к. в этой сборке только LSTM-данные установлены. PSM 6 теоретически должен хуже
  работать на таблицах (читает поперёк колонок), но на практике все три PSM одинаково споткнулись
  на одной и той же шапке таблицы («По выраженности» → «ВЫРаженности | [о фазе...») — это предел
  точности Tesseract на мелком тексте в конкретной ячейке, не PSM-артефакт.
- **Grayscale/autocontrast/бинаризация не улучшили результат** (проверено на `1003_1`, худшем из
  двух файлов по качеству) — узкое место не контраст, а фактическое разрешение скана.
- **Основной текст (не таблицы) распознаётся качественно** на обоих файлах — сплошные абзацы
  клинического текста вышли из OCR без искажений, визуально проверено на рендере страницы.

**Вывод:** `pytesseract.image_to_string(img, lang="rus", config="--psm 3")` при `dpi=300`, без
препроцессинга — простейшая конфигурация, тюнинг не даёт измеримого выигрыша на этих данных.
Точечные искажения в таблицах (единичные слова/ячейки) — принятый tradeoff первой итерации: полный
текст страницы кладём как обычный текстовый чанк (решение уже согласовано — OCR всей страницы, без
реконструкции структуры таблицы).

## Архитектура

Новый модуль `src/RAG/ingestion/ocr.py` — вся логика растеризации страницы и вызова Tesseract,
изолирована от `data_loader.py` для читаемости/тестируемости (аналогично тому, как tabula-логика
уже инкапсулирована в блоке `iter_chunks`).

```python
# src/RAG/ingestion/ocr.py
_TESSERACT_LANG = "rus"
_OCR_DPI = 300

def ensure_tesseract_available() -> None:
    """shutil.which("tesseract") is None → RuntimeError с чётким сообщением
    (что установить и как, аналогично java для tabula)."""

def ocr_page(page: fitz.Page) -> str:
    """Растеризует page.get_pixmap(dpi=_OCR_DPI) → PIL Image → pytesseract.
    Любая ошибка (растеризация или сам tesseract) → перехватывается ВНУТРИ,
    возвращает "" — вызывающий код трактует как «текста нет», как и раньше."""
```

### Точка встраивания

`data_loader.py`, существующий постраничный цикл сбора текста (`iter_chunks`, блок
«Collect full document text»):

```python
for page_idx in range(len(doc)):
    ...
    fragment = page.get_text("text", clip=clip_rect).strip()
    if len(fragment) < _OCR_MIN_CHARS:
        ocr_text = ocr.ocr_page(page)
        if ocr_text:
            fragment = ocr_text
    if fragment:
        full_parts.append(fragment)
```

`_OCR_MIN_CHARS = 50` — новая константа в `data_loader.py`, рядом с `PDF_EXTENSION`/`PDF_PREFIX`.
Детекция **постраничная** (не на уровне всего документа) — покрывает и полностью сканированные
документы, и смешанные (часть страниц — цифровой текст, часть — вклеенные сканы/фото).

### Фатальный vs нефатальный отказ

- **Отсутствие бинаря `tesseract`** — фатально и громко: `ensure_tesseract_available()` вызывается
  один раз при старте инжеста (в `load_documents()`, до цикла по файлам) и роняет весь прогон с
  понятным сообщением. Обоснование: если бинаря нет, каждая сканированная страница провалится
  одинаково — молчаливая деградация по каждой странице только шумит в логах и маскирует
  системную проблему окружения (тот же урок, что с `java` для tabula, но здесь решили не повторять
  ту же тихую деградацию).
- **Ошибка растеризации/OCR конкретной страницы** (повреждённый page object, tesseract упал на
  конкретном изображении) — нефатально: try/except внутри `ocr_page()`, лог в том же формате, что
  `[data_loader] tabula error — ...`, страница даёт пустой текст, документ продолжает обрабатываться.

### Таблицы на сканах

Без изменений в логике: `find_tables()` (векторный детектор pymupdf) не находит ничего на
сканированной странице (нет векторной структуры) → `table_pages` для неё пуст → tabula не
вызывается → вся страница идёт через обычный текстовый путь (с OCR-фоллбеком). Специальной ветки
не требуется.

## Зависимости

- `requirements.txt`: `pytesseract`, `Pillow`.
- Системно: пакет `tesseract-ocr` + языковые данные `tesseract-ocr-rus` (Debian/Ubuntu:
  `apt-get install -y tesseract-ocr tesseract-ocr-rus`). Задокументировать рядом с существующим
  упоминанием Java (README/CLAUDE.md — где сейчас описана зависимость от Java для tabula).

## Тестирование

- `tests/test_ocr.py`:
  - `ensure_tesseract_available()` кидает `RuntimeError`, когда `shutil.which("tesseract")` даёт
    `None` (мок).
  - `ocr_page()` на синтетическом изображении с известным текстом (сгенерировать через PIL
    `ImageDraw`/встроенный шрифт в тесте) — проверяет, что текст действительно распознаётся
    (round-trip), не сравнение точь-в-точь (OCR не детерминирован до символа).
  - `ocr_page()` на повреждённом/невалидном входе → `""`, не исключение.
- Интеграционный тест на живых `206_2.pdf`/`1003_1.pdf` — вне дефолтного `pytest`-прогона
  (медленно, ~50с+ на файл): либо `@pytest.mark.slow` с явным флагом для запуска, либо отдельный
  ad-hoc скрипт для ручной проверки. Дефолтный CI не должен тянуть системную зависимость Tesseract
  ради него.

## Что не делаем в этой итерации (осознанно)

- Не реконструируем структуру таблиц на сканах (page-level OCR как plain text — согласовано).
- Не тюним PSM/препроцессинг для конкретных «плохих» файлов — бенчмарк показал, что выигрыш
  незначителен относительно сложности.
- Не поднимаем облачный OCR/vision-LLM — сознательный выбор в пользу локального Tesseract
  (см. «Зачем» выше).
