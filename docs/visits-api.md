# Visits API (`/visits`)

Pull-API для организаций, интегрирующихся с medkard: трафик сервис-сервис
через приватный WireGuard-туннель, аутентификация — единый bearer API-ключ,
привязанный к конкретным организациям (`api/auth.py`). Каждый роут
принимает `?org=<название>` (регистр не важен) — так указывается нужная
организация.

Роуты реализованы в `src/api/routes/visits.py`; проверить любой из них
можно скриптом `scripts/test-visits-route.sh` — с мок-данными, без
написания клиента.

## GET /visits/check

Дешёвая проверка количества карт за дату. Параметры запроса: `date`
(`YYYY-MM-DD`), `org`.

Возвращает JSON:

```json
{"date": "2026-07-01", "count": 42}
```

Интегрирующийся сервис обычно сравнивает `count` с тем, сколько строк он
загрузил в прошлый раз, и при расхождении повторно вызывает `pull`.

Фильтр по врачу на `/visits/check` сознательно отсутствует — текущий
консьюмер (шедулер Искры) в персональной рассылке `/check` не вызывает
(гвард по Redis + дедуп по имени файла); параметр добавится, когда появится
реальный кейс.

## GET /visits/pull

Возвращает проаудированные карты за дату как xlsx-файл (не JSON) —
интегрирующийся сервис сохраняет файл и пропускает его через свой
собственный RAG-пайплайн загрузки. Параметры запроса: `date`, `org`.

- `200` — `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`,
  `Content-Disposition: attachment; filename="report_<org>_<date>.xlsx"`
- `404` — нет карт для этой организации/даты

Опциональный параметр `doctor_code` — код врача из 1С (`Прием.Врач_код`):
отчёт сужается до карт одного врача, имя файла получает суффикс
`_doc<код>` (`report_<org>_<date>_doc<код>.xlsx`). При нуле карт с фильтром
возвращается **200** и одноклеточный xlsx «За <DD.MM.YYYY> приёмов врача с
кодом <код> не обнаружено» — интегрирующийся сервис доставляет врачу файл
в любом случае. Без фильтра контракт прежний: `404` при нуле карт.

`doctor_code` валидируется (`min_length=1`, только `[\w-]`, до 64 символов);
пустое или невалидное значение → `422`, поэтому интегратор не должен
шаблонить параметр безусловно.

## GET /visits/export

Постраничный JSON-экспорт «сырых» (не обязательно проаудированных) данных
карт. Параметры запроса:

- `org` — обязателен
- `since` — опционально, только карты, обновлённые строго позже этого времени
- `limit` — макс. число строк (`0` = без ограничения)
- `cursor` — смещение для пагинации
- `include_ignored` — опционально, по умолчанию `false` (см. «Статусы карт»)

Возвращает JSON-массив словарей (строк). У каждой строки есть `status`.

## GET /visits/check_updates

Инкрементальная синхронизация: карты, изменённые в указанное время или
позже. Параметры запроса:

- `org` — обязателен
- `since` — опционально; по умолчанию неделя, а НЕ вся история

Карты `ignored` приходят здесь **всегда**, флага нет: у этого роута ещё
нет боевых потребителей, и оберегать нечего.

Отличия от `export`: граница **включающая** (`>=`), пагинации нет.
Клиент хранит курсор сам и должен быть идемпотентен по `card_guid` —
карта ровно на границе придёт повторно.

## Статусы карт

`export` и `check_updates` отдают исход обработки одним полем `status`:

| Значение | Что это |
|---|---|
| `done` | карта прошла аудит, три массива `*_result` заполнены |
| `pending` | данные есть, аудит ещё не отработал — массивы пусты |
| `ignored` | карта намеренно исключена из аудита фильтром |

`ignored` — не мусор и не сбой. Фильтры (`src/audit/filters.py`) стоят по
просьбе самих клиник, в частности главврача: не гонять пайплайн по
визитам, где нет врачебного описания для проверки (лабораторные панели,
инструментальные исследования, отфильтрованные коды МКБ). В `card_data`
у таких карт лежит полная запись из 1С — то есть диагностическая часть
истории пациента, — пусты только `formal_result` / `diag_result` /
`icd_check_result`.

Где какие карты приходят:

| роут | `ignored` |
|---|---|
| `check_updates` | всегда |
| `export` | только при `include_ignored=true` |

Разница историческая, а не смысловая: на `export` уже сидят боевые
потребители, и их набор строк менять нельзя — поэтому там opt-in. У
`check_updates` таких потребителей нет.

Для истории пациента карты `ignored` нужны обязательно — иначе получите
консультации без исследований, на которые они опираются. Получив их,
фильтруйте статистику аудита (доли, замечания, качество) по
`status = 'done'`: у `ignored` результатов проверки нет, и в знаменателе
они всё исказят.

Карты со стектрейсом вместо данных (`broken`) не отдаются никогда, флаг
на них не влияет.

## GET /visits/doctors

Уникальные врачи организации по данным карт (`Прием.Врач_код` +
`Прием.Врач`). Параметры запроса: `org`. Карты с `broken = TRUE` и без
`Врач_код` не учитываются; ignored-карты, наоборот, учитываются — врач в них
настоящий, даже если визит не аудировался. При разных написаниях ФИО у одного
кода берётся самая свежая карта. Сортировка по имени.

```json
[{"code": "00012", "name": "Губарева Елена Александровна"}]
```

## POST /visits/push

Принимает от 1C-организации одну обновлённую карту, чтобы она попала в
ближайший ночной аудиторский батч, не дожидаясь планового pull-а.
Параметр запроса: `org`. Тело: сырой JSON карты (тот же формат, что 1C
шлёт в остальных местах).

Валидация:
- отклоняется (`422`), если отсутствует `Прием.GUID`
- отклоняется (`422`), если в карте нет ни одного из ключей
  `Пациент`/`Услуги`/`Диагнозы` — это расценивается как пустая оболочка, а
  не реальный визит (пустые значения в этих ключах допустимы, отклоняется
  только полное отсутствие ключей)

При успехе карта сохраняется со статусом «в очереди»
(`storage/done_cards_storage.py`) и возвращается:

```json
{"card_guid": "<guid>", "status": "pending"}
```
