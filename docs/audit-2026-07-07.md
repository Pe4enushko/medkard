# Аудит проекта medkard

> Комплексный аудит кодовой базы по шести направлениям: промпты, архитектура (чистая архитектура), RAG, полнота обработки карт по требованиям ЕГИСЗ, документация, велосипеды/костыли.
> Дата: 2026-07-07. Выполнен роем из 6 параллельных Opus-агентов + синтез.

# Резюме

## Общая оценка

Проект medkard реализует содержательную и профессионально проработанную предметную логику: тексты промптов и inline-docstring'и написаны грамотно, аудит формы 025/у опирается на актуальную нормативку (274н/203н/464н/190н), а схема RAG архитектурно сильна (reverse HyDE, гибрид HNSW+BM25+RRF, файло-скоупленные инструменты). Однако все шесть направлений аудита получили вердикт **major**: качественный замысел систематически подорван на уровне исполнения и инженерной дисциплины. Сквозные проблемы — тихая потеря данных и находок без сигнала (битый JSON → «нарушений нет», отсутствующий `import json` роняет табличные чанки), рассинхронизация кода с документацией и промптами, конфиг-россыпь с тремя разными дефолтами модели. Архитектурные границы существуют только на уровне папок: правило зависимостей инвертировано, DIP отсутствует. Совокупно это ставит под сомнение достоверность результатов аудита — при том, что база достаточно зрелая, чтобы довести её до надёжного состояния точечными и среднеобъёмными доработками.

> **Уточнение по контуру данных** (после первичной версии отчёта): данные пациентов приходят из 1С уже обезличенными, а все LLM/эмбеддинг-модели развёрнуты локально — данные не покидают контур организации. Первоначальные выводы о нарушении 152-ФЗ сняты; в разделе ЕГИСЗ оставлены только замечания о том, что эти гарантии не зафиксированы в коде и документации.

## Промпты к LLM

Все промпты собраны и изучены. В проекте 9 внешних промпт-файлов в `src/LLM/prompts/*.txt`, загружаемых на этапе импорта (`src/audit/diagnosis/validator.py:48`, `src/audit/formal_structure/validator.py:41`, `src/audit/icd_check/validator.py:50`, `src/LLM/visit_classifier.py:22`, `src/LLM/query_generator.py:29`, `src/LLM/icd_prefix_picker.py:23`), плюс 2 промпта, зашитых прямо в код (`src/LLM/decider.py:46`, `src/LLM/chinese_detector.py:112`), плюс англоязычные описания инструментов в `src/LLM/tools.py` и `src/LLM/rag_agent.py:42`, которые тоже попадают в контекст модели. Общее качество текстов высокое (чёткая структура «Роль/Данные/Задача/Формат/Обрати внимание», явные JSON-схемы, инструкции против галлюцинаций), но есть системные слабые места.

### Находки

**1. Мёртвый/рассинхронизированный промпт `diagnosis_validator.txt` (major).**
Файл `src/LLM/prompts/diagnosis_validator.txt` описывает единый валидатор диагноза с инструментом `retrieve` и набором флагов `DX_NOT_SUPPORTED_BY_RECORD`, `ICD_TEXT_MISMATCH`, `DX_TOO_GENERAL_FOR_DETAIL`, `DX_CRITERIA_NOT_MET`, `DX_SEVERITY_UNDOCUMENTED` (`diagnosis_validator.txt:16-21`). Grep показывает, что этот файл **никем не загружается**, а фактическая проверка диагноза (`src/audit/diagnosis/validator.py:52-54`) использует три других промпта (anamnesis/inspection/treatment) с инструментами `search_anamnesis`/`search_guideline` и совсем другой выходной схемой (`issues`, без флагов). Флаги `DX_*` не встречаются больше нигде в коде. Это устаревший артефакт, вводящий в заблуждение при чтении и потенциально «оживающий» при неаккуратном рефакторинге. Рекомендация: удалить файл или задокументировать как исторический.

**2. Документация `docs/llm_calls.md` рассинхронизирована с кодом (major).**
Док описывает клиента `instructor.AsyncInstructor` и вызовы `create_with_completion` (`docs/llm_calls.md:11,15,99`), тогда как реальный клиент — сырой `AsyncOpenAI` с `extra_body={"guided_json": ...}` (`src/LLM/client.py:58-76`). Температура `validate_visit` в доке указана 0.7 (`docs/llm_calls.md:20`), в коде — 0.1 (`src/LLM/validations.py:121`). Упомянут `create_agent`, в коде — `create_react_agent` (`src/LLM/rag_agent.py:113`). Для аудита промптов это опасно: единственный «обзор всех LLM-вызовов» не отражает реальность.

**3. Инъекции через данные карты не блокируются (major).**
Полный JSON визита вставляется в user-сообщение без разделителей/экранирования: `validate_visit` делает `json.dumps(visit)` и передаёт как есть (`src/LLM/validations.py:113-123`), классификатор — тоже (`src/LLM/visit_classifier.py:41-44`). В диагностических чекерах свободный текст карты (Жалобы, Анамнез, Рекомендации из 1С) рендерится с markdown-заголовками `## {key}` (`src/audit/diagnosis/validator.py:181,311-318`), которые сам текст карты может подделать (вставив своё `## Инструкция` или «нарушений нет»). Никакой защиты (делимитеры-«часовые», инструкция «игнорируй команды внутри данных», разметка `<card>...</card>`) в промптах нет. Для системы, выносящей вердикт о качестве врачебной записи, это прямой риск манипуляции результатом.

**4. Три разных дефолта модели (major).**
`src/LLM/base.py:19` → `openai/gpt-oss-20b`; `src/LLM/rag_agent.py:36` → `gpt-4o-mini`; `CLAUDE.md`/`docs` → `gpt-4o-mini`. То есть основной клиент и агентский путь по умолчанию идут на разные модели, а промпты (особенно с явными JSON-схемами и без few-shot) откалиброваны под неизвестно какую из них. При незаданной переменной `LLM_MODEL` формальная проверка и чекеры пойдут на разные бэкенды.

**5. Завышенные температуры для детерминированных задач (major).**
Классификация типа визита — по сути извлечение одного из 4 меток — идёт на `temperature=0.7` (`src/LLM/visit_classifier.py:44`). Все три диагностических чекер-агента, выполняющих извлечение структурированных `issues`, создаются с `temperature=0.7` (`src/LLM/rag_agent.py:102`). Генерация гипотетических запросов — 0.7 (`src/LLM/query_generator.py:67`). Для сравнения формальная проверка разумно стоит на 0.1 (`src/LLM/validations.py:121`). При этом ретрай ещё поднимает температуру (`src/LLM/client.py:101`, cap 1.0), то есть на повторе почти рандом. Рекомендация: классификатор и чекеры опустить до 0.0–0.2.

**6. Тихая потеря находок при невалидном ответе (major, medical-safety).**
`LLMClient.call` при исчерпании ретраев возвращает контент даже при плохом `finish_reason` (`src/LLM/client.py:105`, комментарий «last attempt's content even on bad finish_reason»). Далее парсеры `_parse_findings`/`_load_checker_json` при неудаче возвращают пустой список (`src/LLM/validations.py:92-93`, `src/audit/diagnosis/validator.py:94-95,211`). В аудите пустой список = «нарушений не найдено», то есть усечённый/битый JSON молча превращается в «всё хорошо» — ложноотрицательные результаты без сигнала оператору. Нужен явный маркер ошибки парсинга (не пустой результат) и отдельная ветка обработки.

**7. Непоследовательное вынесение промптов + дублирование (minor).**
CLAUDE.md декларирует «Prompt files live under `src/LLM/prompts/`», но два промпта зашиты в код: системный промпт десайдера (`src/LLM/decider.py:46-51`) и промпт починки китайских символов (`src/LLM/chinese_detector.py:112-118`). Промпт десайдера почти дословно повторяет внешний `icd_prefix_picker.txt` (оба: «Ты — медицинский эксперт... Выбери ОДНУ наиболее подходящую... Ответь ТОЛЬКО значением поля ID»), то есть один и тот же промпт живёт в двух местах в двух форматах. Изменение придётся вносить дважды и рискует разъехаться.

**8. Дублирование инструкций между тремя чекерами (minor).**
Блоки «Обрати внимание» и «## Инструменты/Формат» практически идентичны в `anamnesis_checker.txt`, `inspection_checker.txt`, `treatment_checker.txt` (напр. пункт про повторный приём — `anamnesis_checker.txt:40`, `inspection_checker.txt:39`, `treatment_checker.txt:43`; пункт «Не повторяй тот же запрос» повторён в трёх файлах и ещё раз в `src/LLM/tools.py:57`). Правку нужно синхронно вносить в 3–4 местах. Стоит вынести общий хвост в шаблон/частичный include.

**9. Отсутствие few-shot примеров при малой модели (minor).**
Ни один промпт не содержит примеров вход→выход. Схема выдаётся только текстом-описанием (`anamnesis_checker.txt:18-32`, `diagnosis_validator.txt:11-12`). Для 20B-модели (дефолт `base.py`) zero-shot структурированное извлечение с обязательной дословной цитатой `cite` — хрупкое; 1–2 few-shot примера заметно стабилизируют формат и качество цитирования.

**10. Смешение языков (minor).**
Системные промпты и требуемый вывод — русские, но описания инструментов, которые модель видит в контексте, англоязычные (`src/LLM/tools.py:114-117,133-136,190-195`; `src/LLM/rag_agent.py:43-51`), при этом `_QueryInput.description` требует запрос по-русски (`src/LLM/tools.py:49`). Смешение снижает предсказуемость у небольших моделей и делает термины несогласованными.

**11. Хрупкий парсинг свободного текста там, где доступен guided decoding (minor).**
`visit_classifier`, `decider`, `icd_prefix_picker` работают в режиме свободного текста и разбирают ответ строковыми операциями (`src/LLM/visit_classifier.py:47-49`, `src/LLM/decider.py:68-70`, `src/LLM/icd_prefix_picker.py:65-68`), хотя клиент умеет `guided_json`/enum (`src/LLM/client.py:58-60`). Выход по valid_ids/valid_labels защищён, но при промахе классификатор возвращает `None` и тип визита деградирует до OTHER — лучше ограничить генерацию enum'ом.

**12. Самооценка уверенности как жёсткий гейт + опечатка (minor).**
ICD-чекер полагается на самоназначенную моделью `confidence` с порогом ≥8 (`icd_checker.txt:19,26,31`, `src/audit/icd_check/validator.py:160`) — известно ненадёжный сигнал у LLM, стоит подкрепить правилами/вторым проходом. Плюс опечатка в `anamnesis_checker.txt:39` («эпидемологическом» → «эпидемиологическом»; в строке 8 того же файла написано верно).

## Архитектура (Clean Architecture, Р. Мартин)

### Общая картина слоёв

Кодовая база разбита по техническим папкам (`audit`, `LLM`, `RAG`, `storage`, `integrations`, `parsers`, `reporting`, `api`), но это деление **по механизмам, а не по слоям** чистой архитектуры. Явно выделенного слоя сущностей/домена, отдельного от инфраструктуры, нет. Правило зависимостей («зависимости направлены внутрь, к домену») систематически нарушается: бизнес-правила зависят от конкретной инфраструктуры напрямую, без абстракций.

Фактический граф зависимостей (→ = «импортирует»):

```
scripts/*  ─┐  (композиция, но не полная)
            ├→ audit.pipeline ──→ storage.done_cards_storage (конкретный класс)
            │                └──→ parsers.json_parser
            │                └──→ audit.diagnosis / formal_structure / icd_check
            │
audit.*  ───┬→ LLM.client / LLM.tools / LLM.decider / LLM.chinese_detector  (конкретные)
            └→ storage.models.result  (сущности лежат в инфраструктуре!)
LLM.*  ─────┬→ RAG.retrieval.*  (векторный поиск)
            └→ storage.*_storage  (LLM.tools дергает БД напрямую)
RAG.*  ─────→ storage.*
parsers.* ──→ audit.models / audit.filters   ← обратное ребро (цикл на уровне пакетов)
reporting.* ─→ storage.base (наследует инфраструктуру) + parsers.excel
api.routes ─→ reporting.api_formatter  (тонкий контроллер — единственный чистый слой)
```

Домен здесь оказывается в самом центре зависимостей лишь номинально: направление стрелок на практике идёт **наружу**, а не внутрь.

### 1. Сущности живут внутри инфраструктуры (инверсия наоборот)

Бизнес-сущности `Result`, `DiagnosisResult`, `FormalFinding`, `FormalStructureResult`, `DiagnosisIssue`, `IssueSource`, `IcdCodingIssue` физически определены в `src/storage/models/result.py:1-170` — то есть **внутри пакета хранилища**. Доменный модуль `src/audit/models.py:11` импортирует свои же сущности ИЗ storage:

> `from storage.models.result import DiagnosisResult, FormalFinding, FormalStructureResult, DiagnosisIssue`

и честно признаётся в причине (`src/audit/models.py:9`): «live in storage.models.result to avoid circular imports». Это прямая инверсия правила зависимостей: домен зависит от инфраструктурного пакета ради собственных типов. По Мартину сущности должны быть самым внутренним кольцом, о котором не знает ничто снаружи; здесь наоборот — домен тянет их из внешнего кольца.

### 2. Бизнес-правила зависят от конкретной инфраструктуры напрямую

Ни одного протокола/интерфейса между `audit/*` и инфраструктурой нет — везде конкретные классы:

- `src/audit/pipeline.py:33` → `from storage.done_cards_storage import DoneCardsStorage` (конкретный psycopg-класс, инстанцируется в `__aenter__`, `pipeline.py:59`).
- `src/audit/diagnosis/validator.py:29-31,42` → `LLM.chinese_detector`, `LLM.client.LLMClient`, `LLM.tools.*`, `storage.models.result`.
- `src/audit/formal_structure/validator.py:24-26` → `LLM.chinese_detector`, `LLM.validations.validate_visit`, `LLM.visit_classifier`.
- `src/audit/diagnosis/clinic_recs.py:17-18` → `LLM.decider`, `LLM.icd_prefix_picker`.
- `src/audit/icd_check/validator.py:21-23` → `LLM.client`, `LLM.tools`, `storage.models`.
- `src/audit/excel_formatter.py:30` → `from storage.base import BaseStorage` (правило аудита наследует инфраструктурный базовый класс).

Правила аудита не выражены в терминах абстракций «репозиторий карт» / «LLM-судья» / «поиск по рекомендациям»; они жёстко привязаны к OpenAI-клиенту, LangGraph-агентам и Postgres.

### 3. `base.py` — это НЕ интерфейсы, а конкретные базы (DIP отсутствует)

Задание предполагает, что `src/storage/base.py` и `src/LLM/base.py` могут быть точками инверсии зависимостей. Это не так:

- `src/storage/base.py:41-55` — `BaseStorage` — конкретный класс с общим пулом psycopg (`_get_shared_pool`, `src/storage/base.py:27-38`), читает `POSTGRES_*` из окружения (`src/storage/base.py:17-24`). Ни `ABC`, ни `Protocol`, ни `abstractmethod`. Это базовый класс переиспользования кода, а не контракт.
- `src/LLM/base.py:27-33` — `get_openai_client()` — фабрика конкретного `AsyncOpenAI` + константа `MODEL` (`src/LLM/base.py:19`). Тоже конкретика.

Единственная настоящая абстракция во всей кодовой базе — `EmbeddingAdapter(ABC)` в `src/RAG/retrieval/embeddings.py:38-44` с `@abstractmethod embed()` и реализациями OpenAI/ST/fastembed. То есть паттерн инверсии в проекте понимают и умеют применять, но применили его **только** к выбору провайдера эмбеддингов, тогда как для LLM-клиента и хранилища (главные границы между доменом и инфраструктурой) абстракций нет.

### 4. Конфигурация читается внутри модулей, композиции в точке входа нет

`os.environ`/`load_dotenv()` разбросаны по инфраструктурным и доменных модулям: `src/LLM/base.py:17,19,31`, `src/storage/base.py:12,17-24`, `src/LLM/client.py:139` (`AGENT_MAX_STEPS`), `src/RAG/retrieval/embeddings.py:30,33-34`, `src/RAG/retrieval/vector_store.py`, `src/integrations/one_c.py`. Конфиг читается при импорте, а не собирается в composition root и не прокидывается внутрь. Точка входа `scripts/audit-one-c-period.py:35-42` импортирует конкретные `AuditPipeline`, `OneCClient`, `ExcelFormatter` и собирает их, но не внедряет ни конфиг, ни коллабораторов — они сами достанут окружение изнутри. `MODEL` фиксируется в момент импорта `LLM.base` (`src/LLM/base.py:19`), сменить модель без переимпорта нельзя.

### 5. Скрытые глобальные синглтоны инфраструктуры на уровне импорта

Инфраструктура «зашивается» в доменные модули на этапе импорта:

- `_client = LLMClient()` создаётся при импорте в `src/audit/diagnosis/validator.py:39`, `src/audit/icd_check/validator.py:27`, `src/LLM/decider.py:24`, `src/LLM/query_generator.py:30`, `src/LLM/validations.py:30`, `src/LLM/chinese_detector.py:40`.
- `_chinese_detector = ChineseDetector()` — `src/audit/diagnosis/validator.py:38`, `src/audit/formal_structure/validator.py:28`.

Это значит, что подменить LLM/детектор нельзя иначе как monkeypatch-ем глобалей модуля; конструкторного шва (DI) нет.

### 6. God-object в pipeline: `_audit_visit`

`AuditPipeline._audit_visit` (`src/audit/pipeline.py:169-319`) — метод на ~150 строк, который смешивает оркестрацию и доменную логику:

- сам конструирует всех коллабораторов (`FormalValidator()` — `pipeline.py:181`, `ClinicRecs()` — `pipeline.py:211`, `DiagnosisValidator(visit)` — `pipeline.py:227`), внедрения нет;
- лезет в приватные детали чужого модуля: `clinic_recs._load_manifest()` (`pipeline.py:213`, приватный метод) и модульно-приватные `_is_age_eligible`, `_patient_age` (`pipeline.py:31,214,213`) — фильтрация манифеста по возрасту выполняется в pipeline, хотя это логика `clinic_recs`;
- считает токены, персистит `done_cards`, обрабатывает «предложенный ICD-код» повторным аудитом (`pipeline.py:271-298`) — всё в одном методе. Это классический god-method оркестратора, который тянет знание о нескольких доменных поддоменах и о хранилище одновременно.

### 7. Тестируемость: швы только через monkeypatch глобалей

Подменить LLM/БД можно лишь патчем module-level имён, а не через интерфейс/конструктор. `tests/test_pipeline_multiple_diagnoses.py:31-32` делает `monkeypatch.setattr(pipeline_module, "FormalValidator", ...)` и `"DiagnosisValidator"`. При этом `_audit_visit` всё равно вызывает **непропатченные** `ClinicRecs()._load_manifest()` и `check_icd_codes()` (`pipeline.py:211-217`) — то есть для карты с диагнозами тест упрётся в реальный манифест и живой LLM. Это подтверждает известный факт (полный прогон падает без инфры): швы неполны, домен нельзя изолировать от LLM/БД без работающей инфраструктуры. Из всех тестов лишь 4 файла вообще используют monkeypatch/mock; хранилище и LLM негде подменить через контракт.

### 8. Циклическая зависимость пакетов audit ↔ parsers

На уровне пакетов зависимость двунаправленная:
- `audit → parsers`: `src/audit/pipeline.py:32` (`parsers.json_parser`), `src/audit/excel_formatter.py:25` и `src/audit/excel.py:2` (`parsers.excel`).
- `parsers → audit`: `src/parsers/excel.py:44` (`audit.models`), `src/parsers/filter_config.py:15` (`audit.filters`).

Импорт-дедлока нет только потому, что затронуты разные модули внутри пакетов, но архитектурно это цикл: слой парсеров знает о домене, а домен — о парсерах. Плюс латентный цикл `audit.models ↔ storage.models.result`, обойдённый переносом сущностей в storage (см. п.1).

### 9. Дублирование сериализации сущностей (нет единого источника правды)

Форма JSON одной и той же сущности «диагноз с источниками» вручную собирается минимум в трёх местах: `src/storage/done_cards_storage.py:35-55` (`_diag_json`), `src/audit/models.py:34-57` (`DiagnosisAuditResult.to_dict`) и в `src/reporting/result_parser.py` (парсинг обратно). Сущность анемична (только `to_dict`/`pretty_format`), а её представление размазано по слоям — при добавлении поля нужно править всё вручную.

### Что сделано хорошо

- `src/api/routes/cards.py:32-70` — тонкие контроллеры: разбор query-параметров и делегирование в `ApiFormatter`, без БД/бизнес-логики (комментарий `cards.py:5-6` это фиксирует как принцип). Это единственная чисто выдержанная граница слоя. Правда, сам `ApiFormatter` (`src/reporting/api_formatter.py:35`) наследует `BaseStorage` и содержит SQL, т.е. слой «представления отчёта» смешан с доступом к данным.

- Модели-датаклассы (`storage/models/result.py`) типизированы и удобны как DTO.

## Схема работы с RAG

Полный цикл: ингест PDF клин.рекомендаций (`RAG/ingestion/data_loader.py`) → генерация 3 гипотетических запросов на чанк (reverse HyDE, `LLM/query_generator.py`) → эмбеддинг (`LLM/embed_queries.py` → `RAG/retrieval/embeddings.py`) → хранение в `docs` (pgvector, migration `002_docs.sql`) → гибридный ретрив HNSW+BM25+RRF (`RAG/retrieval/vector_store.py`, `searches.py`) → инструменты агентов (`LLM/tools.py`) → ReAct-агенты-чекеры (`LLM/rag_agent.py`). Архитектура продумана, но ключевая идея (reverse HyDE с тремя интентами) на ретриве не реализована, и есть два конкретных дефекта, роняющих часть базы и втрое раздувающих стоимость ингеста.

### Критично / major

**1. Две трети reverse-HyDE не используются на ретриве — стоимость ингеста ×3 впустую.**
На ингесте генерируются и эмбеддятся три запроса (`fact_q`, `procedure_q`, `constraint_q`) и создаются три HNSW-индекса (`002_docs.sql:27-37`). Но на ретриве читается только `fact`-колонка:
- `rag_agent.py:56` хардкодит `query_type="fact"`;
- `vector_store.py:145` — у `_vector_search_filtered` дефолт `col="fact_q_embedding"`, а `_hybrid_filtered` (`searches.py:59`) не передаёт `col` вовсе;
- `search_procedure`/`search_constraint` (`vector_store.py:189-202`) не вызываются нигде (проверено grep'ом).

Итог: 2/3 LLM-вызовов генерации запросов, 2/3 эмбеддингов, 2/3 объёма хранения и 2 из 3 HNSW-индексов — чистые накладные расходы без единого обращения. Либо задействовать procedure/constraint-колонки (роутинг интента запроса), либо перестать их генерировать и хранить.

**2. Баг: `import json` отсутствует в `query_generator.py` — все табличные чанки теряются.**
`_render_content` (`query_generator.py:49`) для `chunk["type"]=="table"` вызывает `json.dumps(...)`, но модуль `json` не импортирован (в шапке файла его нет, `query_generator.py:18-30`). На любом табличном чанке — `NameError`, который перехватывается общим `except` в `ingest-pdfs.py` (`_process_chunk`), чанк логируется как ошибка и возвращается `None`. Практически это значит, что **таблицы клин.рекомендаций (схемы дозирования, критерии, показатели) вообще не попадают в RAG** — при том что `data_loader.py` тратит tabula на их парсинг. Тихая потеря данных.

**3. HNSW + пост-фильтр по `file_id` без тюнинга `ef_search` — риск обвала recall на таргетированном поиске.**
`_vector_search_filtered` (`vector_store.py:166-177`) делает `ORDER BY {col} <=> $1 ... WHERE file_id=$2 [AND section LIKE ...] LIMIT n`. `hnsw.ef_search` нигде не выставляется (grep пусто), дефолт 40. HNSW сначала берёт ~40 глобально ближайших соседей по всему корпусу всех документов, и только потом фильтрует по `file_id`. Для запроса, ограниченного одним руководством среди многих, чанки нужного документа могут не попасть в top-40 → вернётся сильно меньше `TARGETED_TOP_K*6=24` кандидатов или ноль. Плюс к этому фильтры `section LIKE '%...%'` и `chunk NOT LIKE '%Список литературы%'` (`vector_store.py:63,158-162`) ещё сужают выборку уже после HNSW. Нет ни частичного индекса по `file_id`, ни `SET LOCAL hnsw.ef_search`, ни iterative scan. Классическая проблема post-filtering в pgvector; для документо-ограниченного поиска (основной путь чекеров) — прямой удар по полноте.

### Существенное по качеству

**4. `temperature=0.7` на детерминированной задаче мед-аудита.** Агент-чекер (`rag_agent.py:102`) и генератор запросов (`query_generator.py:68`) работают на 0.7. Для аудита соответствия клин.рекомендациям высокая температура повышает вариативность выводов и риск галлюцинаций, ломает воспроизводимость. Стоит понизить (0–0.2).

**5. Псевдо-гибрид: BM25 только по кандидатам вектора.** `_bm25_rank` (`vector_store.py:214-220`) строит `BM25Okapi` заново на каждом запросе по 24–60 уже отобранным вектором кандидатам. IDF считается по кандидатам, а не по корпусу; лексический recall ограничен тем, что уже нашёл вектор. Если вектор не поднял релевантный чанк — BM25 его не «спасёт». Это reranker, а не полноценный гибрид (нет отдельного лексического индекса/поиска, напр. `tsvector`/GIN).

**6. Рассогласование метаданных `section` между текстом и таблицами.** Для текстовых чанков `section` извлекается регэкспом нумерованных заголовков (`_SECTION_PATTERN`, `data_loader.py:46,121-140`), для табличных — из PDF-оглавления `get_toc()` (`data_loader.py:231`). Две разные системы дают разные строки section для одного документа, а фильтры `searches.py` матчат по `section LIKE '%жалоб%'/'%исследов%'/'%лечен%'` (`searches.py:170-196`) — часть таблиц/текста может не попадать под нужный фильтр.

### Стоимость и эксплуатация

**7. Нет батчинга эмбеддингов и кэша.** `OpenAIEmbeddingAdapter.embed` (`embeddings.py:60-65`) шлёт по одному тексту за HTTP-запрос; `embed_queries` (`embed_queries.py:40`) — 3 отдельных вызова на чанк; ингест гоняет по 3 чанка (`QUERY_GENERATION_BATCH_SIZE=3`). Никакого кэша запросов/эмбеддингов. На больших наборах — много round-trip'ов и лишняя стоимость. OpenAI-эндпоинт поддерживает батч `input=[...]` — не используется.

**8. Актуализация базы примитивная, риск устаревшего контента.** Единственный путь — ручной `scripts/ingest-pdfs.py`; дедуп по `get_ingested_file_ids()` (`docs_storage.py:164`). Если PDF обновили, сохранив тот же `ID`, файл будет **пропущен** (уже в базе) → в RAG останется старая версия. Нет версионирования, хеша файла/manifest, инвалидции. Обновление требует ручного `delete_by_file_id` + переингест.

**9. Нет эвала RAG в этом репозитории.** Скриптов/тестов оценки качества ретрива или чанкинга не найдено. Согласно памяти проекта, эвал клин.рекомендаций перенесён в отдельный `engine` и с dev-машины инфраструктура недоступна — то есть здесь качество ретрива фактически не измеряется.

**10. Документация и комментарии рассинхронизированы с кодом (риск ошибок при смене модели).**
- `docs/rag.md:27-34` показывает, что OpenAI-адаптер передаёт `dimensions=EMBEDDING_DIM` — в коде (`embeddings.py:60-65`) этого параметра НЕТ.
- `002_docs.sql:5` комментарий «1024 (Qwen3-Embedding-4B)» — у 4B размерность 2560; дефолтная модель на деле `Qwen3-Embedding-0.6B` (`embeddings.py:34`).
- `embeddings.py:102` комментарий «размер эмбеддинга 1536», рядом `dim=1024`.
Размерность 1024 в трёх местах (env, миграция, кастомная fastembed-модель) не связана — при смене модели рассинхрон почти гарантирован.

**11. Инструкция-префикс Qwen3-Embedding не применяется.** Модели Qwen3-Embedding рекомендуют `Instruct:`-префикс к запросам. Ни запрос ретрива, ни гипотетические запросы ингеста префикса не получают (`embeddings.py:60-124`). Симметрия reverse-HyDE частично сглаживает, но это отход от рекомендованного использования модели — субоптимальный recall.

### Что сделано хорошо
- Разделение табличных и текстовых регионов через `find_tables()` + `clip` (`data_loader.py:90-113`) — таблицы не «протекают» в текстовые чанки.
- Natasha-токенизация для русского BM25 (`vector_store.py:207-211`).
- Аккуратный откат частичного ингеста при прерывании (`ingest-pdfs.py`, `delete_by_file_id` по недокоммиченному файлу).
- Корректный URL-encode пароля в DSN (`vector_store.py:73-84`).

## Полнота процесса обработки карт по требованиям ЕГИСЗ (строго)

### Что проверялось и как

Сопоставлены актуальные нормативные требования к электронной медицинской документации амбулаторного звена с фактической реализацией. Ключевой факт по нормативке: форма 025/у по приказу №834н с 01.09.2025 отменена и заменена приказом Минздрава №274н от 13.05.2025 — и в коде источники правил уже ссылаются на `274n` (`src/audit/formal_structure/rules.json`), то есть нормативная база правил актуальная. Однако система по своей природе — это инструмент **контроля качества/полноты содержания** карт, а не медицинская информационная система: она **не участвует в жизненном цикле электронного медицинского документа** (СЭМД/РЭМД/УКЭП) и не проверяет его.

### Главный вывод по охвату ЕГИСЗ

Требования 947н (ведение МД в форме ЭМД: подписание УКЭП, регистрация в РЭМД в течение 1 рабочего дня, формирование в виде СЭМД по схемам, метаданные) **вообще не входят в предмет аудита**. Аудит смотрит только на текстовое наполнение разделов формы 025/у и клиническую обоснованность, но не на то, подписан ли документ УКЭП, зарегистрирован ли в РЭМД, соответствует ли СЭМД. Ни одного упоминания УКЭП/РЭМД/СЭМД/подписи в `src/` нет (проверено grep). Как «аудит по требованиям ЕГИСЗ» покрытие частичное: закрыт слой «форма 025/у как текст», не закрыт слой «электронный документ ЕГИСЗ».

### Контур данных (152-ФЗ)

**Уточнение по факту** (первичная версия отчёта ошибочно констатировала нарушение 152-ФЗ): данные пациентов приходят из 1С **уже обезличенными**, а LLM и эмбеддинг-модели развёрнуты **локально** — данные не покидают контур организации, поэтому передача во внешние сервисы и ПДн в логах не являются нарушением. Остаются замечания уровня «зафиксировать гарантии»:

1. **Контур не закреплён в коде.** Клиент ходит на произвольный `OPENAI_BASE_URL` (`src/LLM/base.py:31-32`) без валидации, что endpoint локальный; обезличивание выполняется на стороне 1С и кодом никак не проверяется (grep по `redact|anonym|обезлич` в `src/` пуст — защитной логики второй линии нет). Случайное переключение endpoint или изменение выгрузки 1С молча превратит текущий безопасный контур в передачу данных наружу.

2. **Контур не описан в документации.** README/CLAUDE.md не фиксируют, что модели должны быть локальными, а вход — обезличенным; для нового разработчика или проверяющего это ключевой факт о системе.

3. **Аудит доступа отсутствует.** В `src/api/auth.py` — один общий Bearer-ключ, привязанный к набору организаций (`api_key_organizations`), без персонификации пользователя. `src/api/app.py:15-18` не добавляет ни middleware, ни журналирования запросов; в `migrations/` нет таблицы журнала доступа. Даже для обезличенных данных полезно уметь ответить «кто, когда, к какой карте обращался».

## Велосипеды и костыли

Аудит `requirements.txt`/`requirements-api.txt` и обход `src/`, `scripts/` на предмет самописного кода, дублирующего уже подключённые или общедоступные библиотеки. Разделяю находки на «явно переписать», «спорно» и «оправдано (не трогать)».

### 1. `instructor` в зависимостях, но НЕ используется — а рядом два самописных парсера JSON из ответов LLM

`instructor` объявлен в `requirements.txt:3`, но `grep` по `src/` не находит ни одного импорта. Вместо него:

- Самодельный «structured output» через `extra_body={"guided_json": response_model.model_json_schema()}` в `src/LLM/client.py:59-60` — работает только на vLLM-совместимых бэкендах, не на самом OpenAI API.
- Два независимых ручных экстрактора JSON из текста ответа, дублирующих друг друга почти дословно:
  - `src/LLM/validations.py:47-93` — `_json_candidates()` + `_parse_findings()`: снятие ```-фенсов регэкспом, поиск первого `[`/`{`, `JSONDecoder().raw_decode`, откат на «legacy root wrapper».
  - `src/audit/diagnosis/validator.py:74-95` + `200-244` — `_load_checker_json()` + `_parse_issues()`: та же логика (фенсы, поиск маркера, `raw_decode`), плюс ручная пересборка `IssueSource`.

Это ровно та задача, ради которой в проект уже затащили `instructor`: `client.chat.completions.create(response_model=...)` возвращает валидированный pydantic-объект, ретраит по ошибкам валидации сам, работает и с OpenAI, и с self-hosted. Замена убрала бы ~150 строк ручного парсинга и оба «candidate-перебора».
Трудозатраты: средние (переписать `LLMClient.call` + удалить оба парсера). Выгода: высокая — это самый чистый костыль в кодовой базе.

### 2. `src/integrations/one_c.py` — самописный HTTP на `urllib.request` вместо `httpx`

`src/integrations/one_c.py:6-8,57-71`: ручная сборка HTTP-запроса на `urllib.request` — вручную base64-кодированный Basic-auth (`:57`), ручной `urllib.parse.urlencode` (`:58`), ручная склейка URL с выбором сепаратора `?`/`&` (`:59-60`), ручной разбор `URLError`.

`httpx` уже есть в `requirements.txt` (в секции Tests). `httpx.Client(auth=(login, password)).get(url, params={...}, timeout=...)` делает всё это в одну строку: Basic-auth, urlencode, разбор ответа. Плюс синхронный `urllib.urlopen` вызывается из async-пайплайна (`scripts/audit-one-c-period.py`), т.е. блокирует loop; у `httpx` есть `AsyncClient`.
Трудозатраты: низкие. Выгода: средняя (меньше ручного кода, ретраи «из коробки», неблокирующий вариант). Нюанс: `httpx` придётся перенести из Tests-секции в основные зависимости и добавить в `requirements-api.txt`, если API его дёргает.

### 3. Конфиг через `os.environ` россыпью + `load_dotenv()` в каждом модуле; DSN дублируется в двух форматах

`load_dotenv()` вызывается независимо минимум в 5 модулях: `src/LLM/base.py:17`, `src/integrations/one_c.py:13`, `src/storage/base.py:12`, `src/RAG/retrieval/embeddings.py:30`, `src/RAG/retrieval/vector_store.py:35`. Переменные читаются напрямую `os.environ[...]` в 24 местах (`grep`), с рассыпанными дефолтами.

Строка подключения к одной и той же БД собирается вручную дважды в двух форматах:
- `src/storage/base.py:17-24` — psycopg keyword-формат (`host=... port=...`).
- `src/RAG/retrieval/vector_store.py:73-84` — URL-формат `postgresql://...` с `quote_plus` пароля.

Оба читают один набор `POSTGRES_*`. `pydantic` уже в зависимостях; `pydantic-settings` (не подключён) дал бы единый `Settings`-класс с типами, дефолтами и валидацией, а DSN считался бы один раз. Дефолт модели тоже рассинхронизирован: `src/LLM/base.py:19` → `"openai/gpt-oss-20b"`, `src/LLM/rag_agent.py:36` → `"gpt-4o-mini"`, а CLAUDE.md обещает `gpt-4o-mini` — классический симптом конфига-россыпью.
Трудозатраты: средние. Выгода: средняя-высокая (единый источник правды, типизация, конец рассинхрону дефолтов).

### 4. `migrations/migrate.sh` — самописный раннер миграций без учёта применённого + коллизия номеров

`migrations/migrate.sh:13-18` — ручной парсер `.env` (тот же, что делает `python-dotenv`), `:30-39` — прогон всех `[0-9]*.sql` подряд через `psql`. Нет таблицы версий: каждый запуск применяет ВСЕ файлы заново (спасает только идемпотентность DDL, которая на практике не гарантирована — см. `002_docs.sql` с `CREATE TABLE`). Уже есть коллизия номеров: два файла `013_done_cards_metrics_broken.sql` и `013_icd_check_result_col.sql` — порядок между ними зависит от сортировки glob, что и есть баг самодельного раннера.

`yoyo-migrations` или `alembic` (первое — легче, чисто SQL-файлы + таблица применённых) убрали бы и повторное применение, и неоднозначность порядка.
Трудозатраты: средние (alembic — высокие ради чистого DDL). Выгода: средняя. Честно: не срочно, но коллизию `013` стоит развести руками уже сейчас.

### 5. Дедупликация Excel через reverse-парсинг текста ячеек вместо БД

`src/audit/excel_formatter.py:84-119` `_existing_guids_in_excel()` открывает уже записанный `.xlsx`, идёт по строкам, ищет подстроку `"GUID:"` внутри форматированного текстового блока «Данные карты» и вытаскивает GUID построчно. При этом источник данных — таблица `done_cards` с колонкой `card_guid`, и дедуп логично делать на уровне выборки/множества GUID из БД, а не парсингом собственного же текстового рендера. Хрупко: любое изменение формата ячейки в `parsers/excel.py:146-153` тихо ломает дедупликацию.
Трудозатраты: низкие. Выгода: средняя (устранение скрытой связанности «формат Excel ↔ логика дедупа»).

### 6. Мелочь-баг рядом с темой: `json.dumps` без импорта
