# Технические требования к интеграции МИС/1С с MedCheck и «Искрой»

## 1. Потоки данных и назначение

Интеграция включает два обязательных потока данных. Передача MedCheck в
«Искру» является внутренней частью интеграции и показана только для понимания
пути данных.

### Пакет приёмов за дату

```text
MedCheck  ── GET ?date=YYYY-MM-DD ──►  API МИС или 1С
MedCheck  ◄──── JSON-массив приёмов ──  API МИС или 1С
MedCheck  ─────── данные приёмов ────►  «Искра»
```

### Push проведённого приёма

```text
МИС или 1С  ── POST /visits/push ───►  MedCheck
МИС или 1С  ◄── 200 и card_guid ────  MedCheck
MedCheck    ─────── данные приёма ───►  «Искра»
```

МИС или 1С отправляет каждый проведённый приём в MedCheck отдельным
push-запросом.

## 2. Параметры интеграции

| Параметр | Предоставляющая сторона |
|---|---|
| Адрес API клиники для получения приёмов | Клиника предоставляет MedCheck. |
| Способ доступа и учётные данные API клиники | Клиника предоставляет MedCheck. |
| Адрес API MedCheck для push | MedCheck предоставляет клинике. |
| Код организации | MedCheck предоставляет клинике. |
| Ключ доступа | MedCheck предоставляет клинике. |

Значения в угловых скобках в примерах являются шаблонами. При настройке
используются значения, предоставленные соответствующей стороной.

### Жизненный цикл ключа доступа MedCheck

1. MedCheck создаёт ключ доступа и передаёт его клинике.
2. МИС или 1С использует действующий ключ в заголовке `Authorization` каждого
   push-запроса.
3. При подозрении на компрометацию ключа клиника прекращает его использование.
   MedCheck отключает прежний ключ и передаёт новый.

## 3. API клиники: получение пакета приёмов

Запрос к API клиники имеет вид:

```http
GET <адрес API клиники>?date=2026-08-03
Accept: application/json
```

Параметр `date` имеет формат `YYYY-MM-DD` и определяет дату возвращаемых
приёмов. Параметр используется для повторного получения приёмов за прошедшую
дату при восстановлении обработки.

| Ответ API клиники | Значение |
|---|---|
| `200` | Корневой JSON-массив приёмов. |
| `400` | Параметр `date` передан в неверном формате. |
| `401` или `403` | Доступ к API клиники не подтверждён. |
| `5xx` | Временная ошибка API клиники. |

Ответ `200` должен содержать корневой JSON-массив приёмов:

```json
[
  {
    "Прием": {
      "GUID": "8d96a4da-018a-4d55-a66c-5962643a23dc",
      "NUM": "123456",
      "DATE": "2026-08-03",
      "Врач_код": "00012",
      "Врач": "Иванова Анна Сергеевна"
    },
    "Врач": {"SPECIALIZATION": "Педиатр"},
    "Пациент": {"CODE": "P-000001", "GENDER": "Женский", "AGE": 12},
    "Услуги": [{"КодЕГИСЗ": "B04.031.002", "Наименование": "Осмотр врача-педиатра"}],
    "ДанныеОсмотра": [{"Параметр": "Жалобы", "Значение": "Боль в горле два дня"}],
    "Диагнозы": [{
      "КодМКБ": "J06.9",
      "НаименованиеМКБ": "Острая инфекция верхних дыхательных путей",
      "Детализация": "",
      "ВыявленВпервые": true
    }]
  }
]
```

Один элемент массива соответствует одному приёму. При отсутствии приёмов
возвращается пустой массив `[]`. Заголовок ответа: 
`Content-Type: application/json; charset=utf-8`.

## 4. Структура приёма

| Поле | Тип | Требование |
|---|---|---|
| `Прием.GUID` | строка | Уникальный неизменяемый идентификатор приёма. |
| `Прием.NUM` | строка | Номер приёма в МИС или 1С. |
| `Прием.DATE` | строка | Дата приёма в формате `YYYY-MM-DD`. |
| `Прием.Врач_код` | строка | Постоянный код врача в МИС или 1С. |
| `Прием.Врач` | строка | ФИО врача. |
| `Врач.SPECIALIZATION` | строка | Специализация врача. |
| `Пациент.CODE` | строка | Внутренний код пациента. |
| `Пациент.GENDER` | строка | `Мужской` или `Женский`. |
| `Пациент.AGE` | число | Возраст пациента целым числом. |
| `Услуги` | массив | Каждый элемент содержит `КодЕГИСЗ` и `Наименование`. |
| `ДанныеОсмотра` | массив | Каждый элемент содержит непустые `Параметр` и `Значение`. |
| `Диагнозы` | массив | Каждый элемент содержит `КодМКБ`, `НаименованиеМКБ`, `Детализация`, `ВыявленВпервые`. |

Все поля обязательны. При отсутствии услуг или диагнозов передаётся пустой
массив `[]`. Массив `ДанныеОсмотра` содержит не менее одного элемента.
`Детализация` может содержать пустую строку. `ВыявленВпервые` имеет тип
Boolean: `true` или `false`.

## 5. Идентификация и обновление приёмов

1. Для каждого приёма используется отдельное значение `Прием.GUID`.
2. При исправлении приёма значение `Прием.GUID` сохраняется.
3. Значение `Прием.Врач_код` постоянно для одного врача.

## 6. Push проведённого приёма

Операция `POST /visits/push` выполняется после успешного проведения документа
приёма в 1С. К моменту выполнения операции должны быть сформированы `GUID`,
номер, дата и данные осмотра. При повторном проведении изменённого приёма
операция выполняется повторно.

Каждый запрос содержит один объект приёма из массива, описанного в разделе 3.
Адрес API MedCheck, код организации и ключ доступа предоставляются MedCheck.

```http
POST <адрес API MedCheck>/visits/push?org=<код организации>
Authorization: Bearer <ключ доступа>
Content-Type: application/json; charset=utf-8
```

## 7. Подтверждение доставки и обработка ошибок

При успешном приёме данных MedCheck возвращает `200`:

```json
{
  "card_guid": "8d96a4da-018a-4d55-a66c-5962643a23dc",
  "status": "pending"
}
```

Поле `card_guid` соответствует `Прием.GUID` переданного приёма. Значение
`pending` означает, что приём принят для обработки.

Приём считается доставленным в MedCheck при выполнении двух условий: получен
ответ `200`, а `card_guid` в ответе совпадает с `Прием.GUID` запроса. В этом
случае задача отправки завершается. Значение `pending` не является статусом
завершения обработки в «Искре».

Если ответ не получен, имеет код, отличный от `200`, либо содержит другой
`card_guid`, задача отправки остаётся в очереди. МИС или 1С повторяет запрос с
тем же `Прием.GUID` и ограниченной экспоненциальной задержкой. Повторный запрос
обновляет ранее принятый приём с тем же `GUID`.

| Ответ | Действие |
|---|---|
| `200` | Задача отправки завершается. |
| `401` или `403` | Проверяются ключ доступа и код организации. |
| `422` | Исправляется формат приёма; выполняется повторная отправка. |
| `5xx` или ошибка сети | Планируется повторная отправка. |

## 8. Обезличивание, хранение и удаление приёмов

МИС или 1С выполняет обезличивание до передачи приёма в MedCheck. MedCheck и
«Искра» хранят переданные данные без изменения.

Исправленный приём передаётся повторно с прежним `Прием.GUID`. Удаление или
отмена приёма в МИС или 1С не передаётся в MedCheck: API удаления приёма пока
не предоставляется.
