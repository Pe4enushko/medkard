# ГРЛС — реестр лекарственных средств со статусами РУ

Источник: выгрузка Государственного реестра лекарственных средств
(grls.rosminzdrav.ru → «Выгрузка реестра», xlsx-архив `grls<YYYY-MM-DD>-1.zip`,
~19 МБ, 8 файлов — по одному на состояние записи). Архив в git не кладём.

## Что в БД

- `grls_registry` — одна строка = одна строка выгрузки; 7 статусов (файл
  «Изменённый» — журнал редакций — не грузится). Номер РУ **не уникален**;
  ключ дедупликации/синка — `row_hash`. Смысл колонок — `COMMENT ON COLUMN`
  в `migrations/028_grls_registry.sql`.
- `grls_imports` — журнал загрузок; последняя строка = версия реестра
  (`registry_date` = «по состоянию на …» из выгрузки).
- Производные колонки: `dosage_forms`, `dispensing` (из «Формы выпуска»),
  `is_substance` (фармсубстанции `ФС-…`/«субстанция…» — не препараты; поиск
  их не показывает без `include_substances=True`).

## Импорт

    python3 scripts/import-grls.py grls2026-08-17-1.zip --dry-run     # счётчики без записи
    python3 scripts/import-grls.py grls2026-08-17-1.zip               # полная замена в одной транзакции
    python3 scripts/import-grls.py grls2026-08-17-1.zip --make-dump grls.jsonl.gz   # дамп для engine

После записи скрипт печатает `registry rows after import: N` — это размер
таблицы после дедупликации по `row_hash` (`ON CONFLICT`), а не число строк,
поданных на вставку.

Проверка версии: `SELECT registry_date, status_counts FROM grls_imports ORDER BY id DESC LIMIT 1;`

## Как читать статус

Статус берётся из файла выгрузки; даты его не переопределяют (реестр сам себе
противоречит: есть «Действующие» с датой окончания в прошлом). Даты используются
только чтобы смягчить мёртвый статус относительно даты визита
(`grls.status.status_at`): «Истёкший» с `expires_at ≥ дата визита` → «на дату
визита действовало» — не замечание. «Приостановлено применение», «на
подтверждении», «в иностранных упаковках» — предупреждения, не запрет.
Историю перерегистраций по снимку восстановить нельзя (старая запись затёрта).

## Поиск (`storage.grls_storage.GrlsStorage`, `grls.lookup.lookup_medicine`)

Хранение — как есть; нормализация в запросе (`grls.normalize.normalize_query`
↔ SQL `grls_norm()`: lower, без кавычек/®/™, ё→е, схлопывание пробелов
включая неразрывный, пробелы вокруг «+» убираются). Порядок реестров: МНН →
торговое название → БАД. Результаты сортируются по рангу статуса (живые →
приостановлено → истёкший → исключённый).

Внутри каждого реестра — три уровня (`grls.match.MatchKind`, чистое зеркало
SQL в `_tier_predicate`):

1. **exact** — нормализованное равенство;
2. **contains** — одна строка входит в другую, в любую сторону (врач пишет и
   короче реестра, «Метопролол» при «Метопролола сукцинат», и длиннее,
   «Левотироксин натрия» при «Левотироксин»);
3. **fuzzy** — триграммы, ≥ 0.6 для МНН и ≥ 0.85 для торгового наименования.

Похожесть строки не различает «слово добавили» и «слово заменили», поэтому
одним порогом уровни не заменить: правильный `Левотироксин` даёт 0.650, а
неправильный `Преднизон` — 0.692, то есть верное совпадение лежит НИЖЕ
неверного.

Различители — токены короче трёх символов и любые с цифрой («в6», «d3»,
«в12») — обязаны совпасть **отдельным словом**. Сравнение подстрокой
пропускало «в1» внутрь «в12»: тиамин находился как цианокобаламин.

Уровень возвращается наружу и доходит до ответа: «это МНН» разрешено говорить
только про exact, contains говорит «входит в МНН „…“» и показывает найденное
название, fuzzy прямо сообщает, что препарат не опознан. Известная цена
уровня contains — «Эналаприл» ⊂ «Эналаприлат», разные МНН; отличить это от
солевой формы без словаря веществ нельзя, поэтому уровень и не скрывается.

Поиск идёт по хранимым нормализованным колонкам `inn_norm` / `trade_norm`
(миграция 029, `GENERATED ALWAYS AS (grls_norm(...)) STORED`), а не по
индексам от выражения. Значения вычисляются при записи, поэтому правка
`grls_norm()` требует принудительного пересчёта колонок — сама Postgres их не
обновит.

Стоимость слоёв измерена: [`grls-search-cost-2026-08-23.md`](grls-search-cost-2026-08-23.md).
Коротко — сами слои почти бесплатны (доли миллисекунды из индекса), 99 % цены
худшего случая даёт одно неиндексируемое условие `position(col in q)`, и платим
там не за поиск, а за пересчёт `grls_norm()` на всех 39 тыс. строк.

`inn_status_counts` считает регистрации ТЕМ ЖЕ предикатом, каким нашлись
записи, и отдельно — сколько мёртвых сегодня РУ действовали на дату визита.

## Синк в «Искру» (engine)

Контракт — спека `docs/superpowers/specs/2026-08-17-grls-registry-design.md`
§7: канон = `grls_registry`/`grls_imports`, ключ = `row_hash` (алгоритм

(`grls.dump`). Реализация engine-стороны — отдельная ветка.
