# Diagnosis graph e2e on `eval_broken_cards`

Эти standalone-тесты прогоняют реальные обезличенные карты через
`DiagnosisValidator`: подбор КР, PostgreSQL/RAG, embeddings, опциональный
reranker, реальные LLM-вызовы и скомпилированный diagnosis-граф. Моков нет.

ICD-ReAct намеренно не запускается: он не менялся в ветке diagnosis-графа и его
историческая рекурсия не должна маскировать результат проверяемого компонента.

Выбранные карты и основание выбора лежат в
`e2e/fixtures/eval_broken_cards/cases.json`. Покрыты разные исторические
причины: recursion, context overflow, output length, invalid JSON, отсутствие
`parsed/refusal` и нарушение схемы `issues[0]`.

Запуск из корня репозитория тратит реальные LLM-токены и требует настроенных
PostgreSQL, embeddings и LLM:

Общий runner ищет среди всех `e2e/tests/**/test_*.py` пути, подходящие под
переданный grep-регэксп, печатает полный вывод каждого и запускает следующий
даже после ошибки. В конце он возвращает ненулевой exit code, если упал хотя бы
один тест. Например, весь набор diagnosis graph запускается так:

```bash
e2e/run-diagnosis-graph-tests.sh diagnosis_graph
```

Посмотреть найденные тесты без LLM-вызовов:

```bash
e2e/run-diagnosis-graph-tests.sh --list diagnosis_graph
```

Шаблон применяется к пути относительно корня репозитория, поэтому им можно
выбирать каталог, часть имени либо несколько групп тестов. Регэксп с
метасимволами следует заключать в кавычки:

```bash
e2e/run-diagnosis-graph-tests.sh audit
e2e/run-diagnosis-graph-tests.sh 'missing_parsed|length'
```

По умолчанию тесты выполняются последовательно. Флаг `--parallel` запускает до
четырёх тестовых файлов одновременно; число рабочих процессов можно указать
явно. Вывод каждого файла печатается цельным блоком, без перемешивания строк:

```bash
e2e/run-diagnosis-graph-tests.sh --parallel audit
e2e/run-diagnosis-graph-tests.sh --parallel 8 'audit|diagnosis_graph'
```

Каждый запуск тестов автоматически сохраняет полный объединённый stdout/stderr
в `logs/e2e-YYYY-MM-DD_HH-MM-SS-PID.log`. Содержимое файла совпадает с выводом
в терминале, включая заголовки, результаты отдельных тестов и итоговую сводку.
Команда `--list` тесты не запускает и лог-файл не создаёт.

Другой Python-интерпретатор задаётся через
`E2E_PYTHON_BIN=/path/to/python`.

Таймаут на одну карту по умолчанию — 900 секунд. Его можно изменить через
`E2E_DIAG_GRAPH_TIMEOUT_SECONDS`.
# E2E-тесты аудита: фикстурные приёмы с известными дефектами

21 фикстурная карта, каждая с **одним** нарушением, прогоняется через полный
аудит — тот же `AuditPipeline._audit_visit`, что работает на бою: формальный
валидатор, проверка кодировки МКБ и `DiagnosisValidator`, всё с живой LLM.

Набор покрывает правила, которые затронула ревизия нормативной базы
(ветка `formal-rules-npa-revision`): 11 добавленных правил, 9 оживлённых
и `treatment_dosage_clarity`, переобоснованное с утратившего силу 203н на 1094н.

## Запуск

Нужны поднятая БД (читается справочник клинреков) и доступ к LLM — параметры
берутся из `.env` в корне репозитория. HTTP-API не нужен: тесты не ходят по сети.

```bash
for f in e2e/tests/audit/test_*.py; do python "$f" || exit 1; done
```

Цифра в начале имени — группа: `1-` проверки по приказам, `2-` работоспособность
графа диагноза, `3-` незаполненные поля шаблона. Правило — в `docs/e2e-testing.md`,
раздел «Group prefixes».

Каждый скрипт запускается и отдельно, аргументов не принимает. Прогон тратит
реальные токены: 21 карта × (формальный валидатор + проверка МКБ +
`DiagnosisValidator` по каждому диагнозу).

## Почему сверяется полный набор флагов, а не наличие ожидаемого

Спека `docs/superpowers/specs/2026-08-20-e2e-full-suite-design.md` формулирует
для аудит-тестов правило «ассертить наличие конкретного флага, никогда не точный
список». Здесь оно намеренно не соблюдается.

Проверка на наличие не отличает работающее правило от правила, которое
срабатывает всегда: испорченная карта даст ожидаемый флаг в обоих случаях. Раз
в каждой фикстуре ровно одно нарушение, ожидаемый результат — ровно один флаг,
и правило, срабатывающее без повода, проявится лишним флагом на остальных
двадцати картах и положит их. Так набор ловит и ложные срабатывания, а не только
пропуски.

Плата за это — чувствительность к недетерминизму LLM. Лишний флаг на одной карте
означает либо ложное срабатывание правила, либо дефект фикстуры; и то и другое
стоит разобрать, а не заглушить ослаблением проверки.

## Кейсы на картах с прода

Всё сказанное выше держится на стерильной фикстуре, а её нельзя собрать с
реальной карты: живая запись всегда несёт что-то помимо целевого дефекта.
Такие кейсы ставят `only=False` и проверяют один свой флаг. Взамен экзактного
набора к каждому положительному кейсу идут отрицательные — `present=False`,
где того же флага быть не должно. Без пары проверка на присутствие не отличает
работающее правило от срабатывающего всегда, и вся ценность набора теряется.

Карты с прода обязаны быть обезличены: GUID и код пациента заменяются
фикстурными, из текстов убираются ФИО, даты рождения, адреса и номера
учреждений. Торговые названия препаратов остаются — это не персональные
данные, а без них запись перестаёт быть похожей на настоящую.

`Case.expect` может называть флаг, который ставит код, а не правило из
rules.json (`НЕЗАПОЛНЕНЫ_ПОЛЯ_ШАБЛОНА`, `NMU_CODE_CONTRADICTION`). В промпт
такой флаг не попадает, поэтому этап 1 спрашивает саму проверку вместо
`get_rules` — мис-собранная фикстура падает там же, до первого токена.

## Два этапа прогона

**Этап 1 — разбор, без LLM и без БД.** Для каждой фикстуры проверяется, что
`get_visit_types` определил тип визита так, как задумано, и что правило под
тестом попало в набор `get_rules`. Здесь падает неверно собранная фикстура — до
того, как потрачен хоть один токен. Этот же этап проверяет ровно ту проводку,
которую переделывала ревизия: `visit_types`, `age_group`, `icd_prefixes`. Если
хотя бы одна фикстура не прошла этап 1, этап 2 не запускается.

**Этап 2 — полный аудит.** `AuditPipeline._audit_visit` целиком.

Тип визита всегда **выводится системой** из кода услуги (или из диагноза Z11.1),
а не проставляется тестом в обход — иначе тест проверял бы не тот код, который
работает на бою.

Каждый кейс этапа 2 печатает свой `correlation_id` прямо в строке с именем
кейса — тот же id, что `_traced_card_audit`/`graph_trace.trace_context` кладут
во все записи `logs/graphtraces.jsonl` для этого прогона. По упавшему кейсу
не нужно искать нужный кусок трейса по времени или `card_guid` — можно сразу

```bash
python scripts/checks/dump-graphtraces.py --correlation-id <id>
```

По умолчанию скрипт вычищает дословный текст приёма (`card_data`/
`card_data_priem`/`human_message`) из каждой записи — безопасно приложить к
обсуждению. `--keep-card-data` возвращает эти поля, если разбор идёт локально
и карту нужно видеть целиком.

## Почему нет teardown и нет флагов командной строки

`_audit_visit` вызывает `_upsert_done_card`, но тот выходит сразу, пока
`self._done_cards is None`, а заполняется это поле только в
`AuditPipeline.__aenter__`. Поэтому пайплайн здесь используется **без**
`async with`, в БД ничего не пишется и убирать за собой нечего. Не полагайтесь
на формулировку «`_upsert_done_card` вызывается только из `run_batched`» —
она неверна, защищает именно неинициализированный сторедж.

Флагов командной строки нет намеренно: набор рассчитан на массовый автоматический
прогон, а переключатель, меняющий состав проверок, сделал бы зелёный прогон
значащим разное в разные дни.

## Как добавить фикстуру

1. Собрать карту через `fixtures.base_visit` — формат из
   `docs/clinic-data-requirements.md` §3.
2. Испортить **одно** место. Всё остальное в карте должно быть безупречно, включая
   правила, применимые ко всем типам визита: метаданные, отсутствие заглушек и
   дублей, согласованность услуги и специальности, соответствие текста диагноза
   коду МКБ, орфография, полнота назначений, законный представитель для ребёнка
   младше 15 лет. Перечень с пояснениями — в шапке `fixtures.py`.
3. Проверить, не перекрывается ли целевое правило соседним. Например,
   `НЕПОЛНОЕ_НАЗНАЧЕНИЕ_ПРЕПАРАТА` перекрывает инъекционное правило по всем полям,
   кроме реакции пациента, а код МКБ из перечня 168н тянет за собой флаг
   диспансерного наблюдения.
4. Добавить `Case` в `CASES` своего скрипта и прогнать этап 1 — он дешёвый и
   ловит большинство ошибок сборки.

## Известное ограничение набора

`injection_procedure_completeness` ограничено кодами `A02.*`/`A03.*`. Эта область
досталась от прежней редакции `rules.json` и ревизией не пересматривалась, а в
боевых выгрузках (`mdsgrep`, `alenkagrep`) кодов `A02` и `A03` нет вовсе —
встречаются `A04`, `A16`, `A11`, `A01`. Фикстура проверяет правило таким, как оно
написано; зелёный тест означает «правило исправно», а не «правило достижимо на
реальных картах». Подробности — в шапке `test_audit_interventions.py`.
