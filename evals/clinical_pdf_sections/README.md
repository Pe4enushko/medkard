# Эвал границ разделов клинических рекомендаций

## Зачем

`PDFContentReader` размечает каждый текстовый чанк полем `metadata.section`.
Diagnosis graph затем достаёт критерии качества прямым фильтром по этому полю.
Ошибка границы поэтому одновременно:

- раздувает LLM-контекст чужими страницами;
- скрывает реально существующий раздел от `retrieve_criteria`;
- приписывает приложения, библиографию и OCR-мусор последнему полезному разделу.

Эвал сравнивает legacy-разбиение с текущим кандидатом на одинаковом тексте всех
PDF и считает распределение размеров секций в чанках.

## Запуск

```bash
.venv/bin/python evals/clinical_pdf_sections/analyze.py \
  '/home/okabe/Documents/Всякие пдфки и доки/Минздрав/clinical_pdfs' \
  --jobs 6 --top 20 \
  --output-dir evals/clinical_pdf_sections/baselines/2026-08-21-semantic-allow-list
```

Быстрый корпусный прогон использует PyMuPDF-текст и production chunker, но не
запускает поиск таблиц и Tabula: они не участвуют в распознавании текстового
заголовка, а на 707 документах существенно замедляют эксперимент. Проблемные
документы после общего прогона надо отдельно проверять полным
`PDFContentReader.iter_chunks()`.

`--output-dir` сохраняет пригодный для сравнения baseline:

- `sections-exact.csv`: точное название раздела, медиана и среднее число
  чанков, диапазон и ID клинических рекомендаций через запятую;
- `sections-canonical.csv`: исследовательская сводка с объединёнными вариантами
  нумерации одного названия;
- `guideline-sections.csv`: обратная длинная таблица — какие разделы и какого
  размера найдены в каждой клинической рекомендации;
- `corpus.csv` и `metadata.json`: состав и fingerprint корпуса.

Точная таблица является основным baseline. Канонизация эвристическая и нужна
для поиска общих семейств заголовков, а не для доказательства parser parity.

## Текущий allow-list

Произвольные одноуровневые заголовки не включаются: строки `1. ...` слишком
легко спутать с рекомендациями, строками таблиц и библиографией. Разрешены
только семантически стабильные семейства:

| Семейство | Примеры | Защита от ложных границ |
|---|---|---|
| Библиография | `Список литературы`, `XIII. Список литературы`, `9.Список литературы` | не допускаются dot leaders и номер страницы из оглавления |
| Критерии | ненумерованный заголовок, `8. ...`, `XII. ...`, `Таблица 10.1 - ...` | обязательна точная фраза `Критерии оценки качества`; исключены ссылки `приведены в таблице`, `приказ...` и многострочные строки оглавления |
| Приложения | `Приложение А1. Состав...`, `Приложение Г1 - ГN. Шкалы...` | нужен код приложения и описательное название; голое `Приложение А3/5.` не считается заголовком |

Отступ в начале строки разрешён только semantic allow-list. Для обычных
заголовков `N.N` сохранено legacy-поведение; корпусный эвал обязан показывать
`missing_from_candidate=0` и `added_by_candidate=0`.

## Результат 2026-08-21

Корпус: 707 PDF, 707 прочитаны, ошибок нет.

| Метрика | Legacy | Allow-list |
|---|---:|---:|
| Всего секций | 11 252 | 18 280 |
| Секций крупнее 50 чанков | 190 | 95 |
| Распознанных criteria-секций | 3 | 1 085 |
| Criteria-чанков | 90 | 1 903 |
| PDF с распознанными критериями | — | 631 из 707 |
| Библиографических секций / чанков | — | 637 / 11 126 |
| Секций приложений / чанков | — | 5 308 / 12 789 |

Распределение criteria-секций после allow-list:

- 832 секции — 1 чанк;
- 205 — 2–5 чанков;
- 28 — 6–10;
- 18 — 11–25;
- 2 — 26–50;
- ни одной больше 50 чанков.

Для `359_3.pdf` полный production-парсер вместо прежних 78 чанков под
criteria-паттерном теперь даёт 7 коротких criteria-чанков: общий заголовок,
`8.3`, `8.4` и повторные заголовки таблиц. `Список литературы` содержит 66
чанков, остальные распознанные приложения выделены отдельно. Переполнение было
вызвано библиографией и хвостом документа, а не самой таблицей критериев.

## Технический долг: хвост после списка литературы

Выделение `Список литературы` в отдельную секцию **не означает, что хвост
документа очищен**. В нём всё ещё смешиваются:

- собственно библиография;
- приложения, заголовок которых потерян или испорчен OCR;
- состав рабочей группы и методология разработки;
- связанные нормативные документы;
- алгоритмы, памятки пациенту, шкалы и опросники;
- номера страниц, колонтитулы и другой OCR-мусор.

Сейчас библиографические секции всё ещё содержат 11 126 чанков. Некоторые PDF
вообще не имеют извлечённой строки `Список литературы`: список источников
начинается сразу после criteria-таблицы. Поэтому отдельные criteria-секции всё
ещё достигают 34 чанков, а суммарный criteria-пул одного документа — 83 чанков.

Этот хвост нельзя просто удалить целиком: приложения с алгоритмами, шкалами и
информацией для пациента могут быть полезны другим веткам графа. Нужна
типизация зон документа и политика использования по веткам, а не один общий
фильтр.

Оставшиеся задачи:

1. Научиться находить начало библиографии без явного заголовка, не принимая
   нумерованные строки criteria-таблицы за ссылки.
2. Разделить `bibliography`, `methodology`, `regulatory references`,
   `patient information`, `algorithms` и `scales` на разные типы секций.
3. Оценить OCR-варианты и переносы строк для служебных заголовков; каждый новый
   allow-list прогонять по всем 707 PDF с проверкой numbered-title parity.
4. Ограничить criteria-пул и выбирать применимые таблицы по возрасту, виду и
   этапу помощи до вызова судьи. Сейчас несколько реальных таблиц одного КР
   складываются вместе.
5. Привести retrieval к обещанному в design-doc лимиту: текущий
   `get_section_chunks_by_pattern` возвращает все совпавшие чанки, а
   `retrieve_criteria` строит pool с `limit=None`.
6. После стабилизации схемы переиндексировать `docs`: изменение parser’а само
   по себе не исправляет уже записанную `metadata.section`.
7. Добавить версию схемы ingestion, чтобы смешанный старый и новый индекс был
   виден и не выдавал тихо разные результаты.
