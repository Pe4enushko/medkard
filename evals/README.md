# Эвалы поиска по реестру лекарств

Эвал границ разделов клинических PDF находится отдельно в
[`clinical_pdf_sections/README.md`](clinical_pdf_sections/README.md). Он не
относится к поиску ГРЛС и не использует БД.

## Зачем

Спека engine `docs/superpowers/specs/2026-08-20-grls-integration-design.md`
(§4.5, репозиторий **Искры**, ветка `grls-integration`) закладывает в
`drug_registry` колонку `name_embedding`, HNSW-индекс и фазу эмбеддинга в синке.
Всё это оправдано, только если embedding-модель действительно понимает русские
торговые наименования: «Амоксиклав», «Конкор», «Мексидол» — искусственные слова,
и модель могла не видеть их в осмысленном контексте.

Эвал отвечает на вопрос цифрами до того, как это будет реализовано.

## Устройство

| файл | что внутри |
|---|---|
| `base.py` | доступ к Postgres: запись только в `pg_temp`, дальше сессия read-only |
| `corpus.py` | чтение выгрузки ГРЛС, нормализация, производные тексты записи |
| `embeddings.py` | поход к эндпоинту эмбеддингов, `.env` |
| `methods/` | по классу на способ поиска, общий `SearchMethod` |
| `datasets/` | по классу на набор запросов |
| `run.py` | CLI, связывающий всё вместе |

Способ поиска и набор запросов меняются независимо, поэтому и разнесены:
добавить метод = добавить класс в `methods/` и строчку в реестр; добавить набор
запросов = класс в `datasets/`. Харнесс при этом не трогается.

**Доступ к БД.** Харнесс строит временную таблицу, после чего вызывает `seal()`:
сессия переводится в `default_transaction_read_only = on`, и методы получают
`ReadOnlyDB`, в котором способа что-либо записать просто нет. Это проверяется у
сервера (`SHOW transaction_read_only`), а не декларируется в комментарии.
Таблица — `TEMP`, живёт внутри сессии и исчезает при выходе; в БД не остаётся
ничего, поэтому эвал можно гонять против рабочей базы medkard.

## Запуск

```bash
pip install openpyxl                 # для --from-zip
pip install 'psycopg[binary]'

python -m evals.run --from-zip ~/projects/grls2026-08-17-1.zip
python -m evals.run --from-zip … --dataset handcrafted --limit 0
python -m evals.run --from-zip … --index name --methods trigram,vector
```

Эндпоинт, ключ, модель и параметры Postgres берутся **из `.env` репозитория**
теми же переменными, что использует medkard (`src/RAG/retrieval/embeddings.py`):
`EMBEDDING_BASE_URL` (иначе `OPENAI_BASE_URL`), `OPENAI_API_KEY`,
`EMBEDDING_MODEL`, `POSTGRES_*`. Перебиваются флагами `--base-url`, `--api-key`,
`--model`, `--pg-dsn`. При старте печатается, какой `.env` подхвачен и с каким
эндпоинтом пойдём — свериться до того, как начнётся эмбеддинг.

Полезные флаги: `--limit N` — размер корпуса (по умолчанию 5000; `0` — все
~17 тыс. уникальных названий, честнее и дороже), `--per-level N` — запросов на
класс синтетики, `--dump-queries FILE` — выгрузить запросы для разбора.

**Выгрузка открытых данных (`data-*.csv` / `data-*.json`) не годится**: в ней
ноль торговых наименований и МНН (спека engine §3.3). Только xlsx-архив ГРЛС или
загруженная таблица `grls_registry`.

## Что индексируется

Флаг `--index`:

- **`blob`** (по умолчанию) — `search_blob`: `торговое | МНН | ФТГ | лекформы |
  отпуск | держатель`. Так делает спека §4.5;
- **`name`** — только торговое наименование (узкий эксперимент).

Режим меняет выводы: с blob'ом МНН и ФТГ лежат **внутри** индексируемого текста
и находятся лексикой, поэтому у вектора остаётся меньше работы.

## Способы поиска (`methods/`)

| класс | метод | что делает |
|---|---|---|
| `Trigram` | `trigram` | `pg_trgm` по всему индексируемому тексту |
| `Tsv` | `tsv` | `to_tsvector('russian')` по «остальному» (ФТГ, формы, отпуск, держатель) |
| `TrgmTsv` | **`trgm+tsv`** | **продакшн-кандидат**: триграммы по названиям + tsv по остальному, RRF |
| `Vector` | `vector` | только косинус по эмбеддингу (`pgvector`) |
| `Hybrid` | `hybrid` | `vector` + `trigram` с весом, как в 084: `d_vec + 0.3*d_trgm` |
| `HybridEven` | `hybrid_even` | то же без весов |
| `TrgmTsvVec` | `trgm+tsv+vec` | продакшн-кандидат плюс вектор — что вектор **добавляет** |

`trgm+tsv` — то, что планируется в Искре, поэтому он базовая линия: остальные
методы оцениваются тем, насколько они её обходят. `hybrid_even` нужен потому,
что вес `0.3` подобран под клинреки (747 строк) и на лекарствах может не
подойти: если он заметно лучше `hybrid`, коэффициент надо подбирать свой.

Метод возвращает не готовый SQL, а **выражение сортировки** (`order_by()`,
меньше = лучше). Поэтому все методы считаются одним проходом по корпусу, а не
семью.

### Слияние ранжирований: RRF и почему одного RRF мало

Ветки сливаются как `Σ 1/(K + rank)`, K = 60 — так же, как медкард сливает BM25
с вектором. Сумма рангов проигрывает, когда по запросу одна ветка пустая
(запрос — название, `ts_rank` = 0 у всех): её ранг произволен и подмешивает в
сумму шум.

**Но само по себе RRF от этого не спасает — спасает `dense_rank`.** Первая
редакция считала ранги веток через `row_number`, и мёртвая ветка всё равно
обязана была выдать кому-то ранги 1, 2, 3…, раздавая их по `id`. В RRF такой
ранг весит `1/61` — ровно столько же, сколько точное попадание в живой ветке,
поэтому записи с малым `id` систематически всплывали поверх настоящего ответа.
Причём RRF тут хуже суммы: он сжимает разницу (ранг 1 против ранга 21 —
`0.0164` против `0.0123`), а сумма штрафует пропорционально. Подпись дефекта в
выдаче — `recall@1 = 0.06` при `recall@10 = 0.95`: ответ в топе есть, позиция
внутри топа назначена произвольно.

`dense_rank` (так и в проде, `084_clinical_guideline_name_embedding.sql:76-77`)
схлопывает всю массу нулей в один ранг; он достаётся и эталону тоже, становится
общим слагаемым и сокращается. **Ранги веток — `dense_rank`, итоговая позиция —
`row_number`** (при массовых ничьих `rank` отдал бы всей группе лучшую позицию и
завысил метрику).

**Правило для продакшн-кода Искры:** сливать можно только ранги, в которых
непопадания неразличимы между собой (`dense_rank`) либо вовсе отброшены
(кандидатский список с предикатом совпадения и `LIMIT`). Плотный `row_number` по
всему корпусу в слияние не подавать.

## Наборы запросов (`datasets/`)

### `synthetic` — правила, большой объём

| класс | вход |
|---|---|
| `L0 exact` | точное название; проверка вменяемости |
| `L1 typo` | регистр, ё/е, ®, пробелы |
| `L2 typo1` | одна случайная опечатка |
| `L3 typo3` | три случайные опечатки |
| `L4 phonetic` | русские искажения на слух (о↔а, е↔и, тс↔ц) |
| `L5 inn2trade` | **МНН на входе, торговое в ответе** |
| `L6 ftg exact` | точная ФТГ |
| `L7 ftg typo` | ФТГ с двумя опечатками |
| `L8 ftg partial` | фрагмент ФТГ («противоопухолевое», «средство растительного») |

Оговорка, которую надо держать в голове при чтении цифр: искажения здесь
**случайные, а не человеческие**. `_typo` ставит произвольную букву алфавита во
внутреннюю позицию и ничего не дописывает в конец, поэтому падежного
«мексидола» в наборе нет как класса, а «амокшсклав» человек не напишет. Классы
`L2`/`L3` дают лексике задачу тяжелее реальной и **завышают ценность вектора**.
Реалистичен из набора `L4`.

Отдельно про `L1`: перед лексикой запрос всё равно проходит `grls_norm`, который
складывает и регистр, и ё, — то есть для лексики это no-op. Настоящее содержание
класса в другом: в модель запрос уходит **сырым**, поэтому `L1` меряет
чувствительность эмбеддера к CAPS и ё.

### `handcrafted` — то, что действительно пишут человек и модель

115 искажений, эталон размечен вручную и проверяется при загрузке. Классы:
`inflect` (падеж), `suffix`, `prefix`, `tail`, `dose`, `form`, `translit`,
`mixed`, `phonetic`, `space`, `root`, `dictation` — см. `datasets/handcrafted.py`.

Два узла, из-за которых набор устроен именно так:

- **голого названия в реестре часто нет.** «Креон» существует только как
  «Креон® 10000/25000/40000/Микро», «Мезим» — как «Мезим® форте», «Флемоксин» —
  как «Флемоксин Солютаб». Врач при этом пишет голое имя. Поэтому эталон
  задаётся не только точным совпадением, но и **префиксом**, а класс называется
  `tail`;
- **эталон проверяется при загрузке.** Если запись не разрешается в корпус,
  набор падает с перечислением проблемных запросов. Молчаливая потеря половины
  набора при обновлении реестра выглядела бы как «метод стал лучше».

`--limit` режет корпус случайной выборкой, поэтому при ручном наборе харнесс
возвращает в корпус все записи-эталоны и печатает, сколько вернул. Дистракторы
остаются подвыборкой, то есть задача легче полного корпуса: **для решения о
схеме гонять с `--limit 0`.**

## Множественный ответ и recall

У классов по ФТГ и у `tail` правильных ответов много. Поэтому у каждого запроса
не один эталон, а множество, и ранг считается по **первому релевантному**:

- **recall@k** — доля запросов, где хотя бы один правильный ответ попал в топ-k
  (k = 1, 5, 10);
- **MRR** — среднее от `1/ранг` первого релевантного;
- **|gold|** — средний размер множества правильных ответов.

Корпус не сокращается под запрос: score считается против **всех** записей.
Из-за разного `|gold|` **классы между собой сравнивать нельзя** — сравнивать
надо методы внутри одного класса.

## Как читать результат

Отталкиваясь от `trgm+tsv`:

- **`trgm+tsv+vec` не лучше `trgm+tsv`** — вектор не добавляет ничего поверх
  того, что и так будет. Колонку `embedding`, HNSW-индекс и фазу эмбеддинга из
  спеки убрать.
- **Выигрыш вектора только на `L5`/`L6`** (МНН и точная ФТГ) — взвесить трезво:
  в режиме `blob` оба поля лежат внутри индексируемого текста. Прогнать оба
  режима, `blob` и `name`, чтобы увидеть разницу.
- **Выигрыш на классах искажения названия** — вот это настоящий довод за вектор,
  и считать его надо по `handcrafted`, а не по `L2`/`L3`.
- **`L8 ftg partial`** отвечает на отдельный вопрос: находится ли препарат по
  куску названия группы. Если проседает у всех методов — в промпте подагента
  проговорить, что ФТГ надо называть целиком.
- **`hybrid_even` заметно лучше `hybrid`** — вес `0.3` из 084 под лекарства не
  подходит, подбирать свой.

Результат прогона записать в спеку engine (§4.5) с датой и версией модели:
вывод зависит от модели эмбеддингов, и при её смене эвал надо повторить.
